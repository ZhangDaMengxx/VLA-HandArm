# 灵巧手调试页使用说明

> **调试记录，含历史结论。** 当前驱动限位为拇指弯曲 0.48、四指 1.333；Web 手模型
> 挂载自 `assets/viz/hand/`。下文关于 `assets/inspire_hand/`、0.6/1.47 和旧生成脚本
> 的段落仅保留排错背景，当前状态以 `sim/inspire_hand.py`、`sim/app_web.py` 和根目录
> `PROJECT_STATUS.md` 为准。

## 概述

在 app_web.py 新增第三个模式**「灵巧手调试」**,用于单独调试 Inspire RH56DFX 灵巧手：
- 独立于「实时 Live」模式,不需要机械臂、不需要 ROS2 bridge
- 只需要 pyserial + conda lerobot 环境,手的 RS485 串口通了就能用
- 显示手的 URDF 3D 模型(含 mimic 耦合,手指弯曲看得对)
- 右侧滑块设定 6 个驱动关节目标角,拖动只动 3D 预览,点『下发』才写串口
- 进页面即出 3D(离线也能拿滑块预览姿态),接入串口是另一个动作
- 遥测面板显示温度/电流/力/电压/故障等寄存器
- 左侧竖排 tab 栏(接入/关节/速度力控/预设动作/录制/技能包),一个按钮对应一个可切换的框,
  切页记住上次停在哪栏;右侧只留只读监视(实际角度 + 遥测),交互全部挪到左边
- 「录制」栏:拖滑块摆姿态 → 点『记录当前姿态』存一帧 → 存成技能包(手势)文件 → 「技能包」栏按名字/路径回放
  (关节滑块在「关节」和「录制」两栏都能用,摆姿态和存帧不用来回切)
- 「视频」栏:人手视频 → MediaPipe → 重定向 → 自动挑关键帧 → 一键送进录制器,做一遍动作就能存成手势

## 架构

```
浏览器                 app_web.py                    后端子进程
  ↓                       ↓                              ↓
点「灵巧手调试」    (只加载 3D,不开串口)      three.js 在浏览器里跑,无子进程
  ↓                       ↓
点「接入灵巧手」    HandDebugSession.start()    ┌─ hand_console.py(独占串口 RS485)
  ↓                       ↓                       │    ↓ stdout JSON
点「下发」          POST /api/hand/command      │    └→ 广播给 WebSocket /ws/hand
  ↓                   写 console stdin            │
WebSocket ← 实时遥测 ← pump_console               └─ 退出时自动复位手到安全张开位

拖动滑块 → 不出浏览器(只改本地值 + three.js 预览)
```

摄像头实时模仿走独立的连续控制路径，不再逐帧追加 HTTP 硬件请求：

```text
MediaPipe → /ws/hand/mimic → retarget → 3D 预览
                                  └→ latest-only mailbox(30Hz)
                                         ↓ 等真实 ACK，最多一条在途
                                    hand_console → ANGLE_SET
```

等待 ACK 时只保留最新目标；WebSocket 断开会清掉待发目标，且同一时刻只有一个摄像头
会话能取得硬件控制权。HTTP fallback 只维持 retarget 和 3D 预览，WebSocket 恢复后才继续
驱动真手。连续控制时角度反馈保持 30Hz、力反馈降到 10Hz，全量温度/电流/状态在目标空闲
500ms 后补读，避免遥测读事务抢占控制写事务。

- `hand_console.py`: Python 3 系统解释器,只依赖 pyserial,独占 `/dev/ttyUSB0`
- `hand_rerun.py`: conda lerobot 解释器(有 pinocchio / rerun),从 console stdin 读 JSON

## 使用步骤

### 1. 启动 Web

```bash
source ~/ros2_ws/robot_host_env.sh
~/gradio_venv/bin/python sim/app_web.py
```

浏览器打开 `http://<WSL_IP>:7860`。

### 2. 切换到「灵巧手调试」

顶栏点第三个 tab **灵巧手调试**。

页面布局：

```
┌ 78px ─┬──── 336px ────┐                    ┌── 312px ──┐
│⚡接入 │                │                    │ 实际角度   │
│⇅关节 │  当前 tab 的    │    3D 视口          │ ANGLE_ACT │
│◐速度 │  面板内容        │   (全屏背景)        │ 厂商通道序 │
│☰预设 │                │                    │ 遥测      │
│⏺录制 │                │                    │           │
│🎬视频 │                │                    │ 只读监视   │
│⬒技能包│                │                    │           │
└───────┴───────────────┘                    └───────────┘
```

左侧竖排 tab 栏,一个按钮对应一个面板盒。**所有交互都在左边**;右侧只留只读监视。

关节滑块盒在「关节」和「录制」两栏都出现,但那是**同一个 DOM 节点在搬家**,不是两份
拷贝(`mountSliderBox()`)。两份拷贝要么撞 id,要么得双向同步 —— 同步写漏一处就会出现
"滑块显示 A、录进去的是 B"这种最难查的错。搬家天然只有一个真值。

为什么右侧留只读而不是全塞进 tab：摆姿态/录制时要同时看设定值和实际反馈,塞进
tab 里一次只能看一个,对照就断了。

选中的 tab 存 `localStorage.handTab` —— 切到别的页再回来还在原来那栏,不会把
录制中的人弹回「接入」。方向键 ↑↓ 在 tab 栏内循环切换(WAI-ARIA tablist 行为)。

窄屏(<1400px)只留图标,标签文字先牺牲,功能不砍。

### 3. 接入灵巧手

「接入」栏点**「接入灵巧手」**按钮：
- mock 模式(默认): 无硬件空跑,滑块能拖、3D 能动,用于验证 UI 和协议
- 真手模式: 改 `startHandDebug()` 里的 `mock = false`,需要 `/dev/ttyUSB0` 通且 24V 供电

接入后:
- 按钮变绿显示「断开」
- 状态从「离线」变成「在线」
- 中央 3D 视口加载手的 URDF,显示实时关节角

### 4. 控制关节

「目标角度设定」盒 —— 滑块是**设定值**,不是读数:

- **拖动不发报文**,只更新数字 + 3D 预览(纯本地,零延迟)
- 点 **下发到灵巧手** 才把 6 个角度打包成一条 `{cmd:"angles",rad:[6]}` 写 ANGLE_SET
- **读回实际**: 用当前 ANGLE_ACT 覆盖滑块,当微调起点
- 卡头右侧显示「已修改 · 未下发」/「已同步」

实际角度只在上面那张「实际角度 ANGLE_ACT」卡里显示,**不会覆盖滑块**。

> 为什么不做拖动即发:一次拖拽能产出几十个 POST,每个都要排进 hand_console 的 50ms
> 主循环等一次串口往返;同时 20Hz 的遥测帧又把滑块值刷回实际角度,拖起来像跟橡皮筋
> 拔河。改成显式下发后,单次命令生效 ≈50ms(一个循环周期),拖动本身完全不过网。

3D 的取值来源:滑块处于「未下发」状态时显预览值,否则跟实际角度走 —— 否则刚摆好的
姿态会被下一帧实际值立刻抹掉。

速度/力控:
- 拖动速度滑块 → 调 SPEED_SET 0-1000,不断电保存
- 拖动力控滑块 → 调 FORCE_SET 0-1000 g

快捷按钮:
- **归零(张开)**: 六个关节全取 URDF 下限 = 完全打开的平手(含拇指侧摆 0)
- **清除错误**: 写 CLEAR_ERROR 寄存器

### 5. 查看遥测(2026-08-06 改版)

右侧「逐指读数」是**一根手指一行**的表,列组用分段按钮切换:

| 组 | 列 |
|---|---|
| **力** | 条形 + 力 g + 峰值 |
| **角度** | 条形 + raw(0-1000) + rad |
| **状态** | 态 + 温度 °C + 电流 mA |

下方**常驻安全行**(切到任何组都显示):最高温 + 最大力 + 故障位。
过温 `ERROR` Bit1 **不可清除**、只能等凉,所以它不许被藏在别的 tab 后面。

为什么切换而不是一行铺开 6 列:实际要看的是"横向扫一眼哪根手指受力",
那要求一指一行;6 个数字列在右栏里挤不开,拆两行会变成 12 行交错反而扫不动。

**采样率不一样,别混**:
- **力每帧读**(约 29Hz,只 1 个寄存器 ~3ms)。抓握时力会冲高再落回,
  1Hz 采样在一次 1-2 秒的抓握里只有 1-2 个点,峰值靠运气、系统性低估
- 温度/电流/状态/电压走**全量遥测 1Hz**(8 个寄存器,贵;这些量变化慢,够用)
- 角度 20-30Hz

**峰值列**是 `|力|` 的会话内历史最大值,「峰值清零」按钮或断开重连会归零。
条形按峰值**自动缩放**(下限 400g),满格对应多少 g 写在脚注 —— 写死分母不行,
同一动作在不同 speed/force 下峰值差 2 倍以上(笔在 500/500 下食指 2270、
在 200/305 下 1059)。

**着色阈值**(实测来的,见下文「力控语义」):力 >200 红、>60 蓝;温度 ≥58 红、≥50 蓝。

> ⚠ 修过一个静默错位 bug:`telemetry()` 原来**不做通道换序**,于是同一页上关节滑块
> 是项目序(拇指在前)、力/温度/电流是厂商序(小指在前),而显示时只是 join 成一串
> 数字没有逐指标签,所以看不出来 —— 把小指的力读成拇指的。现在 `telemetry()`
> 保证全部 6 通道数组都是**项目顺序**并额外回 `channels` 数组当权威来源。
> mock 分支反而一直是项目序的(它从 `_target_rad` 算),所以改之前 mock 和真机
> 互相矛盾,拿 mock 永远测不出这个 bug。

### 6. 预设动作序列

列表来自 `~/ros2_ws/inspire_hand/动作序列文件/DefaultAction.txt`,13 个序列。
**接入之前就能看到列表**(它是文件内容),点某一项才需要会话在跑。

### 7. 录制手势技能包

「录制」栏。流程：去「关节」栏拖滑块摆姿态 → 回「录制」栏点**「⏺ 记录当前姿态」**
→ 攒够帧 → 填名称和路径 → **「保存技能包」**。

一帧存的是:6 关节角(rad + raw 两份)+ 速度 + 力控 + 驻留时间。

**录制来源**两种：
- **滑块设定值**(默认)—— 你手里正在拖的那份。没接手也能纯靠 3D 预览编一整套
- **实际反馈** —— 用手把灵巧手掰到某姿态,录它实际停在哪。要先接入

每帧行上的按钮：`↑` 上移 · `◉` 预览(灌回滑块 + 3D,**不发串口**)· `⟲` 用当前姿态
替换 · `×` 删除。帧名和驻留时间可以直接在行内改。

**「3D 试播」**按驻留时间顺序在 3D 里播一遍,完全不发串口 —— 离线校验时序用。

### 8. 回放技能包

「技能包」栏列出根目录下所有包,每个包：`▶` 回放 · `✎` 载入录制器编辑 · `⭳` 导出
到本机 · `×` 删除。

**「按名称复现」**输入名字直接执行 —— 这是留给以后语音/VLA 的入口。**重名不猜**:
返回 409 + 候选路径列表,让调用方指定 `path`。猜一个的话,同名两个包哪个被执行取决于
文件系统遍历顺序,那是不可预期的机械动作。

回放和预设动作**共用同一个播放器**,所以同时只能播一个,暂停/继续/停止那三个端点也
是同一套。

**回放前先回零位**(默认开,存在包里的 `return_home_first`)：回放起点固定,第一帧
的运动路径可预期。关掉的话,如果当前姿态离第一帧很远,第一步就是一次大幅快速运动。
回零帧的驻留是 `HOME_HOLD_MS = 500`ms。

⚠ 这一栏只列**手势包**(`data/gestures/`)。臂+手联合录制包是另一种,在合体页,见
`COMBO_DEBUG.md` —— 它走同一个 `ActionPlayer`(手侧复用 `gesture_play`),但
`return_home_first` **强制 `False`**:它的第 0 帧就是录制那一刻的姿态,回零会插一段
**臂不知道的**手部运动,两侧时间轴当场错开。

### 9. 从视频解手势(MediaPipe)

「视频」栏。做一遍动作录成视频,解出关节角,挑关键帧,直接变技能包 —— 不用手拖滑块。

链路:`视频 → MediaPipe 21 关键点 → dex_retargeting → 6 个驱动关节角`。三块都是复用
已有的,没重写：`single_hand_detector.py` / `hand_estimators.py` /
`configs/inspire_hand_right_local.yml`。

流程：
1. 选视频(`data/` 下的 + 上传的临时文件),或点「上传」
2. 设 `stride`(抽帧间隔,30fps 下 stride=3 ≈ 10Hz)和最多解析帧数
3. 选「哪只手」—— 选错了会一帧都检不出
4. 「开始解析」,进度 500ms 轮询一次。MediaPipe 单帧约 50ms,200 帧约 10s
5. 解完自动挑关键帧;「逐帧时间轴」可以拖着看每一帧(灌 3D + 滑块,**不发串口**)
6. 「送进录制器」(替换)或「追加」→ 到「录制」栏填名字保存

**解析只读视频,不碰硬件。** 解出来的角度要下发得先存成技能包再显式点回放。

#### 挑关键帧的阈值用 L∞ 而不是欧氏距离

阈值 `eps` 是 6 关节角差的 **L∞**(任何**一根**手指动超过阈值就算新姿态)。

欧氏距离会把"一根手指大动"和"六根手指各微动"算成一样大,而前者是新手势、后者是抖动。
手势的语义靠单指的位置,不靠总体位移量。

默认 `eps=0.25` rad ≈ 14°,比 MediaPipe 自身抖动大一档,又足够分开"张开/半握/握紧"。
实测在测试视频上：`eps=0.1→20 帧, 0.25→11, 0.5→9, 1.0→3`,单调不增。

#### 「全部帧」和「只挑关键帧」两种模式

要**复现连续动作**就用「全部帧」(默认)。关键帧模式只留几个定格姿态,中间过程全丢了,
回放是一顿一顿的 —— 那个模式是给「几个定格手势」用的。

30fps 素材 `stride=1` 时「全部帧」一秒 30 帧,回放和源视频逐帧对齐。

#### 驻留时间取相邻帧的真实时间差

这样回放节奏和视频里做动作的节奏一致。

下限是 `PLAYER_TICK_MS`(回放器的时间分辨率),上限 `HOLD_MS_CEIL = 2000`ms
(超过的一律是漏检空档,不是真实节奏,照搬会让回放莫名停顿几秒)。

界面上会显示 `源 X s → 回放 Y s · 倍率 N×`。有拉伸就该让人看见,而不是默默慢放。

⚠ `stretch` 指标**只统计帧间间隔**,不把末帧的 `default_hold_ms` 算进去。算进去的话
它在分子分母各出现一次,会把真实拉伸**稀释**掉 —— 曾经把 4× 的失真报成 1.48×,
那个数看起来"还行",于是真正的问题被藏住了。

## 回放时序:三个坑,都踩过

「回放看起来很延迟」这个现象查下来是三个独立的原因叠加,每个都会单独造成明显慢放。

### 1. 驻留下限凭空拍了 80ms

原来 `hold_ms` 夹到 `[80, 5000]`。30fps 素材 `stride=1` 时帧间 33ms,被抬到 80ms
就是整段**慢 2.4×**。

下限该等于回放器的 tick 周期(比一个 tick 短的驻留落不到实处),不该再额外加慢放。
各 stride 下的实测：

| stride | 真实帧间隔 | 旧夹取后 | 倍率 |
|---|---|---|---|
| 1 | 33ms | 80ms | **2.40×** |
| 2 | 67ms | 80ms | **1.20×** |
| 3 | 100ms | 100ms | 1.00× |

所以旧代码只有 `stride≥3` 才是原速 —— 而 `stride=3` 恰好是我设的默认值,所以一开始
没发现。要连贯就得 `stride=1`,一调就撞上 2.4× 慢放。

### 2. 播放器 tick 率和遥测率绑在一起

`ActionPlayer.tick()` 是在 `hand_console` 主循环里被调用的,所以**遥测率就是回放的
时间分辨率**。原来 `--hz 20` → tick 50ms,想回放 33ms/帧的素材根本不可能。

而且 `hold_ms` 和 tick **同量级时是最坏情况**：循环落在截止时刻前一点点就要再等一整个
tick,于是 33ms 的驻留时而 33ms、时而 66ms。实测 tick=33ms 播 33ms/帧素材:180 帧
跑成 8.10s(源 5.97s,慢 1.36×)。

修法是把两者**拆开**：`--hz 30` 发遥测,`--player-hz 100` 跑播放器。tick 10ms 对
33ms 驻留是 ~10% 量化误差,而浏览器仍只收 30 帧/秒的遥测,不会被 100Hz 的 JSON 灌爆。

两个常量在 `gesture_pack.py`(`CONSOLE_HZ` / `PLAYER_HZ`),`app_web.py` 起 console 时
从那里取。`test_console_hz_matches_spawn_arg` 锁着这个引用关系 —— 两处写死不同的数字
会让时序算错而**毫无报错**。

### 3. 截止时刻从 `now` 累加,量化误差会攒起来

这是最隐蔽的一个。`ActionPlayer.tick()` 原来是：

```python
self._wait_until = time.monotonic() + step.delay_ms / 1000.0   # ← 从 now 起算
```

tick 10ms、驻留 33ms 时,实际触发在 40ms(`ceil(33/10)*10`),而下一步又从这个
40ms 起算 —— **每步都多 7ms**,整段慢 1.21×。拆开 tick 率之后仍然慢,就是这个原因。

改成从**上一个截止时刻**累加(绝对时间轴)：

```python
base = self._wait_until if self._wait_until else now
self._wait_until = base + step.delay_ms / 1000.0
if self._wait_until < now:                    # 落后太多就重新对齐
    self._wait_until = now + step.delay_ms / 1000.0
```

触发点变成 40/70/100/140…,平均正好 33.3ms,误差不累积。

那个"落后太多就重新对齐"是必要的：不加的话绝对时间轴会要求"补课",连续几个 tick
每次都发一步 —— 手根本走不到位,姿态直接被跳过。宁可整段稍微拖长,也不能丢姿态。

这条对**预设动作也一样生效**(同一个播放器),修完预设动作的步进偏差从几十 ms 降到 1ms。

### 修完的实测

180 帧 / 源 5.97s 的连贯动作：

| 阶段 | 总时长 | 倍率 | 步间隔中位 |
|---|---|---|---|
| 原始(80ms 下限 + tick 50ms) | — | 2.4× | — |
| 下限改 tick、tick 33ms | 8.10s | 1.36× | 34ms |
| 拆开 player-hz=100 | 7.28s | 1.22× | 41ms |
| 截止时刻改绝对累加 | **5.97s** | **1.000×** | 30ms |

预设动作步进偏差 +1ms;暂停 1.5s 再继续,总时长 = 5.97 + 0.4(末帧驻留)+ 1.5 = 7.88s,
步号连续无跳步。

### 帧数上限也一起放开了

原来按"手拖滑块能录几帧"定的 512,视频连贯轨迹是另一个量级(30fps 下一秒 30 帧)：

- `gesture_pack.MAX_FRAMES` 512 → **2400**(约 80s @30fps)。每帧约 200B,2400 帧
  也就 480KB
- `video_gesture.MAX_EXTRACT_FRAMES` 600 → **2000**
- 前端帧列表改成**事件委派**,并且只渲染前 200 行(`REC_RENDER_LIMIT`)——
  上千个 DOM 行会让每次重建都卡,而人也不会去逐行编辑上千帧。**只限渲染不限数据**,
  超出的照样保存和回放

#### 检不到手的帧跳过,不补零

补零会在时间轴上插进一个"突然张开"的假姿态,挑帧时看不出那是漏检。跳过的话前端能
看到帧号不连续,知道那段没检到。

#### 低通滤波关掉了

`low_pass_alpha=1.0`。低通是给实时遥操作压手抖用的,但它引入延迟 —— 逐帧离线解析时
每帧输出会拖上前几帧的残影,挑出来的关键帧就不是那一瞬间的真实姿态。要平滑的话应该
在取完之后对整条曲线做零相位滤波,不要在这里做单向的。

#### 12 个 dof 里按名字取 6 个

重定向输出 12 个 dof(含耦合的 intermediate/distal),我们只要 6 个驱动关节。
**按名字取,不按下标** —— dof 顺序由 URDF 决定,写死数字哪天 URDF 改了会静默错位,
角度装到别的手指上,看起来像"重定向不准"。缺关节时直接 raise,不静默降级。

### 10. 断开

再次点按钮「断开」:
- console 收到 `{"cmd":"quit"}`,先复位手到安全张开位(0.8s),再断开串口
- Rerun serve 停止
- 3D 视口清空

## 手势技能包格式 (sim/gesture_pack.py)

```json
{
  "schema": "hand_gesture_pack/1",
  "name": "OK手势",
  "hand": "inspire_rh56dfx_right",
  "joint_order": ["thumb_proximal_yaw_joint", "thumb_proximal_pitch_joint",
                  "index_proximal_joint", "middle_proximal_joint",
                  "ring_proximal_joint", "pinky_proximal_joint"],
  "created_at": "2026-08-03T17:20:29",
  "note": "食指拇指捏合",
  "return_home_first": true,
  "frames": [
    { "label": "预备", "rad": [0,0,0,0,0,0],
      "raw_vendor": [1000,1000,1000,1000,1000,1000],
      "speed": 500, "force": 500, "hold_ms": 600 }
  ]
}
```

`name` 是**按名回放的键**,和文件名各自独立。手改文件时改 `name` 不影响文件路径。

### 为什么 rad 和 raw 两份都存

- `rad` 是项目关节序(`HAND_JOINTS`),人能读、能直接喂 3D 预览、能手改
- `raw_vendor` 是厂商通道序(m=0 小指 … m=5 拇指旋转),是真正写 `ANGLE_SET` 的值

回放**以 raw 为准**,做到位级一致。只存 rad 的话每次回放都要重算 rad→raw
(夹取 + 取整),来回几趟会漂。手写的文件没有 `raw_vendor` 就从 `rad` 推。

### 两个字段必须表示同一个姿态

存帧时 raw 会**折一趟 rad 再回来**(`GestureFrame.build`),前端 `normRawVendor()`
做同样的事。不折会怎样：

`thumb_pitch` 的 `RAW_MAP` span 是 0.698 rad,而 URDF 上限是 0.6 —— 量程比限位宽。
所以 raw 120 要求 0.6144 rad,超限位。`rad` 字段被夹到 0.6,`raw_vendor` 却还留着 120。
于是 3D 预览显示 0.6,回放真的走到 0.6144。

会不一致是因为 `ActionPlayer._send_angles()` 在真机上直接 `write_shorts("ANGLE_SET")`,
**绕过** `InspireHand.set_angles()` 的 URDF 夹取。折回之后 raw 变 141(= 0.6 对应的
raw),预览和回放就对上了。

四指反过来:span 1.39626 **窄于**限位 1.47,所以 raw 0 停在 1.39626,到不了 1.47。

### 时序:hold_ms 是下发**之后**的驻留

和 `ActionStep.delay_ms` 语义完全对齐,所以回放能直接把技能包转成 `ActionSequence`
交给现成的 `ActionPlayer` —— 暂停/继续/停止全部白送,时序逻辑不出现第二份实现。

`to_action_sequence()` 里有个必须注意的点：`ActionStep.angles` 是**项目序**,因为
`ActionPlayer._send_angles()` 会再做一次项目→厂商置换才写 `ANGLE_SET`。我们存的
`raw_vendor` 是厂商序,所以要先 `vendor_to_proj()` 转回去。搞错的话手指整体反着动
(拇指的值发给小指),`test_to_action_sequence_angles_are_project_order` 锁着这条。

`proj_to_vendor` / `vendor_to_proj` 两个方向**都显式写出来**了。`PROJECT_TO_VENDOR
= [5,4,3,2,1,0]` 恰好是自逆置换(整体倒序),所以现在两个函数算出来一样 —— 但那是
巧合。哪天映射改成非自逆的,依赖"反正一样"的代码会静默把通道写错。

### 路径沙箱

根目录默认 `data/gestures/`,`HAND_GESTURE_DIR` 环境变量可覆盖(比如指到挂载的共享盘)。
`resolve_pack_path()` 是**唯一**的路径入口,web 层所有读写都过它。

四道检查,缺一不可：

1. **逐段白名单** —— 挡 `..`、`/` 开头的绝对路径、Windows 保留字符、点开头的隐藏名
2. **强制 `.json` 后缀** —— 免得写出 `.py`/`.sh` 被别的东西捡去执行
3. **`resolve()` 后必须仍在根内** —— 兜住前两步没想到的组合
4. 第 3 步用 `resolve()` 而**不是** `os.path.normpath`：normpath 是纯字符串运算,
   不看文件系统,根目录里放一个指向 `/etc` 的软链接就能绕过去。`resolve()` 会真的
   跟软链接走,所以软链接逃逸也一起挡了(`test_sandbox_blocks_symlink_escape`)

必须沙箱的原因：**7860 端口没有认证**,同网段任何人都能调。开放任意绝对路径写入
等于给出一个远程任意文件写入的原语。要存到根目录外用「导出到本机」——那是浏览器
原生下载,后端不参与。

写入是**原子**的:先写同目录 `.tmp_*` 再 `os.replace()`。直接 `open(w)` 写一半崩了会
留下半个 JSON,之后每次列表都解析失败,看起来像"包坏了"而不是"上次没写完"。

坏文件**不会让整个列表报错** —— `list_packs()` 给它带个 `error` 字段列出来。一个坏
文件让列表 500 的话,页面上什么都看不到,反而更难查。

## 动作序列文件格式

`DefaultAction.txt` 每 9 行一组:1 行索引号 + 8 行步骤。每步 19 个字段:

```
6 个角度 | 6 个速度 | 6 个力控 | 1 个延时(ms)
```

空白字段(`    ,`)= 该项不设置 = -1。解析时有三个坑:

1. **索引号重复**。13 个序列的索引是 `2,3,4,4,4,3,3,4,4,3,5,5,3` —— 手册说这文件是
   导出快照不是索引表。所以定位必须用 `slot`(文件里第几个),用 index 会永远命中第一个。
2. **空白占位行**。不足 8 步的用 `    ,    ,...` 填满,这种行 strip 后非空,会被解析成
   "全 None + 延时 0" 的空步。不跳掉的话每个序列都报 8 步,播放时前几步瞬间空转。
   实际步数是 2-5 步。
3. **中间两组的顺序没有文档**。手册 2.4.21 只说"包含角度、速度、力控、延时",没说
   6-11 是速度还是力控。当前按 **速度在前** 解析,依据是抓握序列里这一组随着手合拢
   递减(1000 → 500 → 200),符合"边合边降速";而且厂商 demo 也是先设速度再设力控。
   要坐实得写一套已知值下去再读回来对照。

### 时序语义

延时是**下发动作后的驻留时间**(等手走到位),不是下发前的等待。所以第一步立即执行,
之后每步等上一步的 `delay_ms` 到点再走。反过来实现会让第一步白等一个延时,
且最后一步的驻留被丢掉。

暂停时记下剩余驻留,继续时接着走 —— 不是重置成完整延时。

## 力控语义与抓握判据(2026-08-06 全部实测)

这一节是抓握包设计的依据。**每条都是真手量出来的**,推翻了三处此前的推断。

### FORCE_SET 六通道都夹 1000,拇指不例外

手册两个寄存器容易混:

| 寄存器 | 地址 | 手册标称 | 实测 |
|---|---|---|---|
| `FORCE_SET` | 1498 | 0-1000 全通道 | 写 1500 读回 **1000**;800→800、1000→1000 |
| `DEFAULT_FORCE_SET` | 1044 | 0-1000,**拇指 0-1500** | 照收 1500,**四指也收** |

所以"拇指可到 1500"只对 `DEFAULT_FORCE_SET` 成立,而它是**上电默认值**、
**不实时传播**到 1498(实测写 1044 后 1498 不变)。而且 `connect()` 一连上就写
`init_force`,把这条路自己毁了。要走它得写 `SAVE(1005)` 烧 Flash —— handarm_notes
明确写了初始化里**不要**写 SAVE。

`FORCE_MAX` 已按实测改回全通道 1000。逐通道 `set_force` 保留:
"捏鸡蛋要拇指+食指轻、其余不动"是真需求,底层 `write_shorts` 一直是 6 通道的,
是这层 API 之前把它拍平成标量。

### FORCE_SET 管不住刚性接触的力

阈值 40 → 峰值 1014;120 → 1438;300 → 1654。有降低作用,**远不封顶在设定值**。

→ 刚性物体上光靠力阈值做不出"轻捏"。

### STATUS 拿不到 3,抓握成败看力不看态

手册 2.4.19 说 `3` = 力控到位停止。**实测拿不到**:把 `FORCE_SET` 从 300 压到 120
再到 40,让食指被拇指挡死,`STATUS` 全程停在 `2`(位置到位)。手指明显被挡住,
固件仍报"到位了"。

所以 `STATUS=2` 在这个固件上更像"运动停止"的泛称,不区分停止原因。

**判据改用 `FORCE_ACT`**:
- 抓到了:**参与通道的最大值** > ~200(空载校准后 ≤10)
- 抓空了:位置到位但最大值 < ~50

⚠ 必须取**最大值**,不能取平均。拇指旋转在捏的动作里不受力(只负责摆到对掌位),
高速时会给出 70-280 的**伪信号**(惯性),低速下塌到 1-10 —— 取平均会被它污染。

### 空载校准 FORCE_CLB(1009) 有效,但要等稳定

校准前最大偏置 46 → 校准后 **10**(20 次采样完全一致)。脚本
`sim/calibrate_hand_force.py`,**手上不要有东西**。

⚠ 校准后**立刻**采样会读到 175 这种瞬态值,误判成"校准没生效"。要重新张开手 +
等读数连续多次相同再采信。校准结果是否掉电保存手册没写,脚本不写 SAVE。

### 真实抓握数据(拇指+食指捏,29Hz 采样)

| 物体 | speed/force | 拇弯峰值 | 拇弯稳态 | 食指峰值 | 食指稳态 |
|---|---|---|---|---|---|
| 笔(硬) | 500/500 | 493 | 471 | 1243 | 1171 |
| 海绵(软) | 500/500 | 377 | 296 | 971 | 770 |
| 笔(硬) | 200/300 | 341 | 324 | 889 | 832 |
| 海绵(软) | 200/300 | 322 | 278 | 643 | 535 |

**峰值受行程影响、不稳定难重复;稳态只受最终位置(压缩量)决定。**
所以判据和力度目标都用稳态。(同一操作在 1Hz 采样下曾测出食指 2270,29Hz 下是
1243 —— 1Hz 在 1-2 秒的抓握里只有 1-2 个点,那个 2270 是运气好采到冲击峰值。)

**拇弯分不出软硬**(低速下软物 397 > 笔 375),因为它是**静止的砧座**、只读静态
夹持力;食指是运动那根、读静态 + 撞击。软物上两者比值接近 1(牛三定律),
硬物上食指高出的部分就是撞击 —— 刚性物没有形变去吸收它。
→ 想从力反推物体性质时**别用拇弯**。

### 力闭环冻结:机制成立,速度是唯一有效的力度旋钮

冻结 = 把当前 `ANGLE_ACT` 原样写回 `ANGLE_SET`,位置误差归零、电机松劲。
对照组(同动作不冻结)峰值 926 vs 冻结组 728 → **降 21%,机制成立**。

速度扫描(手指互顶,触发阈值固定 150,`sim/test_force_freeze.py --sweep-speed`):

| speed | 触发 | 最终稳态 | 位置过冲 |
|---|---|---|---|
| 300 | 222 | 941 | 4.0 |
| 200 | 189 | 786 | 4.0 |
| 150 | 166 | 717 | 4.5 |
| 100 | 194 | 557 | 3.5 |
| 50 | 160 | **272** | **0.0** |
| 20 | 4s 内没触发(疑超时,未证) | | |

**过冲的成因不是延迟。** 冻结只用 10.6ms、位置只多走 4 counts,力却从 167→720g。
speed 50 时位置过冲 **0 counts** 而力仍涨 112g —— 那部分是**结构弹性变形**
(手指/传动/接触面),不是关节继续转。随速度变的是**动量**。

→ 所以力度档直接映射到 **speed**,不需要力闭环迭代。
  `soft` 50(~272g) · `normal` 150(~717g) · `firm` 300(~941g)

**捏鸡蛋:勉强可行。** speed 50 下 272g vs 鸡蛋点载荷破碎 200-400g,在下限边缘。
这是刚性接触(斜率最陡一档),柔性物同速更轻。

### ⚠ 两种「过冲」别混淆

| | 含义 | 柔性物 | 刚性物 |
|---|---|---|---|
| A 峰值→稳态 | 阻尼消散,力**自己落回** | 13-21% | 5-6% |
| B 触发→稳态 | 检测后力**继续涨** | 待测 | 336% |

A 是材料阻尼(动态力 > 静态力),B 是延迟+动量+弹性变形。
**对力闭环设计 B 才是关键。**

### 拇指-食指干涉:目标点可能在可行域外

同时给六通道下 raw 0,实测 `ANGLE_ACT = [228, 230, 231, 0, 0, 0]`(项目序)。
中指/无名/小指到底,拇指两关节和食指停在 228/230/231 —— 三个不同关节停在 3 个
计数内,是它们**互相顶住**。中指往外、不和拇指相交,所以能到底。

可行域(拇指 yaw=pitch=T,食指命令到 0):

| T | 食指最多能到 |
|---|---|
| ≤300 | ~225 |
| 450 | 52 |
| ≥600 | 0 |

有效变量是 `max(yaw_raw, pitch_raw)` —— **两个关节都收进来才堵,任一个张开就把
拇指带离食指路径**(yaw=0 + pitch=1000 时食指能闭到底)。

**同速下快慢都撞**(speed 100/500/1000 全 JAM),速度比只决定哪一方短:
拇指优先 → 拇指到 0、食指卡 511;四指优先 → 食指到 0、拇指卡 374。

`hand_close` 原值 `[1.0,0.5,1.2,...]` 就命令了这么个不可达姿态(食指目标 raw 141,
实际只到 231)。已改成 `[1.0,0.5,0.95,...]`,实测全部到位(误差 ≤15)。

**2026-08-08:约束已进 schema 校验**(`hand_pose.check_feasible`,加载期跑)。
不可行 = **加载失败**,不是警告 —— 互顶会堵转(ERROR Bit0),顶久了触发过温位
(Bit1,**不可清除**)。宁可清单加载不过,不要真机上闷着烧。

> ⚠ 表里的 **225 是「卡住的位置」,不是「安全到位的位置」**。T3 是把食指命令到
> raw 0、它在 225 处停下来的。所以命令到正好 225 等于让它贴着拇指,再往里就是
> 持续顶。`hand_pose` 的 `limit` 派生状态因此取 **干涉点 +10**(`LIMIT_MARGIN`),
> 10 这个值不是猜的:`hand_pinch` 实测通过的 raw 234 相对 225 就是 +9。

> ⚠ 这张表沿 **yaw = pitch = T** 的对角线扫的。用 `max()` 概括到非对角线,依据只有
> 一个点(yaw=0 + pitch=1000 时食指能闭到底)。对角线之外目前就这一个数据点,
> 要更准得补一次二维扫描。

### 单次读失败率约 40%,要"连续两次一致"

`parse_reply` 原来只验帧头和校验和,**从不核对回复里的寄存器地址**,于是上次查询
的迟到回复被当本次结果。症状:同一寄存器连读三次得三个不同值,其中两次是别的
寄存器的值 —— 校验和全对,因为那确实是合法帧,只是答的是别的问题。

已加地址核对(`parse_reply(raw, want_addr)`)。但地址核对挡不住**同一寄存器的旧值**,
所以静止后取终值仍要"连续两次读到相同"才采信;运动中采样只能用单次读
(要求两次一致会等到停止,就看不到过程了)。

写基本正常(实测至少 1/16 真丢写,其余"失败"是读不到),读才是不可靠的那头。

## 手势规格层(2026-08-08)

清单原来直接写 `hand: [1.112, 0.600, 1.07, 0.0, 0.0, 0.0]` —— 看不出是什么手势、
改一个数不知道会不会撞、每个新手势要上真手量一遍。现在写五指语义,
`skills/hand_pose.py` 在**加载期**展开成六关节弧度。

```yaml
pose: {thumb: opposed, index: limit}      # 捏:拇指对掌 + 食指闭到刚够碰上
```

### 归一量语义

`n ∈ [0,1]`,**0 = 张开/伸直,1 = 这台机器实际能到的最闭**。六通道统一。

满量程取 `min(span, URDF上限)`,所以:

| 通道 | span(xls) | URDF 上限 | n=1 落在 |
|---|---|---|---|
| 四指 | 1.39626 | 1.47 | raw 0(span 更紧) |
| 拇指侧摆 | 1.246165 | 1.246165 | raw 0 |
| 拇指弯曲 | 0.69813 | **0.6** | **raw 141**(丢 14% 行程) |

拇指弯曲那 141 不是 bug,是 URDF 限位比实际行程紧。归一化按有效上限做,
`n=1` 的语义才是"实际能到的头"而不是"理论行程的头"。

### 状态名

四指:`open` 0 / `relaxed` 0.25 / `half` 0.5 / `curled` 0.75 / `closed` 1.0,或直接给数。

拇指两个关节**成对**给。状态值是从**实测通过的清单项反算**的,不是纸面推的:

| 状态 | (yaw_n, pitch_n) | 来源 |
|---|---|---|
| `opposed` | (0.892, 1.0) | 反算自 `hand_pinch` 的 [1.112, 0.600] |
| `folded` | (0.802, 0.833) | 反算自 `hand_close` 的 [1.0, 0.5] |
| `up` | (1.0, 0.0) | 对掌位但不弯 —— 点赞 |
| `open` | (0.0, 0.0) | 躺在掌面 + 伸直 |
| `side` | (0.5, 0.4) | 过渡位,不与食指抢空间 |

> ⚠ yaw 的 `n=1` 是**对掌位**(拇指立起来指向食指,能捏),`n=0` 是躺在掌面
> (指尖最近 47mm,捏不上)。别按"1=收起来"理解 —— 这个通道 1 是"摆过去"。

### `limit`:推导状态

`index: limit` = "食指闭到刚够碰上拇指",由可行域表算出(干涉点 + `LIMIT_MARGIN` 10)。
换拇指姿态,食指自动跟着变 —— 这是"推演"而不是"录制":新的捏类手势不用上手量。

中指/无名/小指的 `limit` = 满弯(T1 实测三根都能到 raw 0)。但那是"六通道同时下 0"
的轨迹,不是拇指先到位的轨迹,所以它们的 1.0 只对速度调好的同时闭合成立。

### 抄表要配核对

`hand_pose.py` **抄了一份** `RAW_MAP` / `HAND_LIMITS`,没 import `inspire_hand` ——
`skills/` 里 import 它要把 `sim/` 塞进 `sys.path`,而 `sim/schema.py` 和
`skills/schema.py` 同名,之前踩过这个遮蔽坑。

抄的代价是会漂(2026-08-07 换 URDF 就漂过),所以配了 `--verify`:用
`importlib.spec_from_file_location` **按文件路径**加载 `inspire_hand` 逐项核对,
不走 `sys.path`。改了驱动那两张表就跑一次。

```bash

```

#### 拇指侧摆 thumb_yaw 的方向(已定)

`raw 0 = 垂直掌面(对掌位)`,`raw 1000 = 完全打开`,即 `invert=True`,和四指同向。

依据是 URDF 几何,不用上手试:

| URDF yaw | 拇指长轴出掌面 | 拇指尖↔食指尖最近 | 含义 |
|---|---|---|---|
| 0.000 | 14° | 47.0 mm | 躺在掌面里,捏不上 → 完全打开 |
| 1.308 | 62° | **8.0 mm** | 能捏 → 对掌位/垂直掌面 |

"能不能捏到"是决定性判据:扫 pitch 0→0.6 × 食指 0→1.47 找拇指尖到食指尖的最近距离,

> 注:URDF 最大外展只到出掌面 62°,不是几何意义上的正 90°。用户口述的"与掌面 90°"
> 指的是那个对掌姿态,端点对应关系是对的,别拿 62° 去质疑映射。

## 时间轴:`t_ns` 权威,不要累加 `hold_ms`(2026-08-03)

`hold_ms` 是 `int`,而 30fps 的真周期是 `1000/30 = 33.3333…ms` —— **无限循环小数,
任何有限位十进制都表示不了**。存成 33 每帧少 0.333ms,而且**单向不抵消**:

| 帧数 | 累加 `hold_ms` 的漂移 |
|---|---|
| 180(6s) | −60 ms |
| 600(20s) | **−200 ms**(实测 199.7) |
| 2400(`MAX_FRAMES`) | **−800 ms** |

方向是**手偏快**(每帧 33 而不是 33.333,整段提前结束)。臂侧按绝对时刻走,
手侧一累加两边就错开 —— **抓取动作里手已经合上而臂还没到位**。

改法:每帧加 `t_ns`(相对包起点的**整数纳秒**),它是权威时刻;`hold_ms` 降为便利字段。
schema 升到 `hand_gesture_pack/2`,读的时候 `/1` 和 `/2` 都收。

**为什么用整数纳秒而不是"多加几位小数"**:小数位越多误差越小但永远不是零,
累加 N 次放大 N 倍 —— 那是压症状不是治结构(素材换成 24 或 120fps 又会露出来)。
整数纳秒是行业做法:ROS 的 `builtin_interfaces/Duration` 是 `int32 sec + uint32 nanosec`,
MP4/FFmpeg 用 `timescale + 整数 tick`,PTP 用秒+纳秒 —— **没有一个用十进制小数存时间**。
残差 0.333ns/帧,2400 帧才 0.0008ms,比臂的控制周期(4.5ms)细 5600 倍。

实测(600 帧 30fps):按 `t_ns` 定位误差 **0.000 µs**,按累加 `delay_ms` **199.667 ms**。

### 三处配套改动

1. **`ActionStep` 加 `t_ns: int | None`**。厂商的 `DefaultAction.txt` 没有绝对时刻,
   所以默认 `None`,那种序列继续走累加那条路
2. **`ActionPlayer.tick()` 按 `t_ns` 定位**。原来那段"从上一个截止时刻累加、
   不从 now 累加"的逻辑是对的(它消掉了 tick 量化误差,注释里有实测数据),
   但它累加的是 33 而不是 33.333 —— 漂移来自**上游的取整**,不是 tick。
   ⚠ `resume()` 里必须把暂停时长累进 `_paused_total`:绝对时轴下不累的话
   恢复瞬间 `now - t0` 已经跑过好几个 `t_ns`,播放器会连着补几步,中间姿态被跳过
3. **`to_action_sequence()` 里 `t_ns` 要加上 home 那一步的偏移**。包里的 `t_ns`
   是"相对包起点"的,而播放器的时间轴从**序列**起点算 —— `return_home_first` 时
   序列前面多一步,不平移的话首帧截止时刻已经过期

### `video_gesture` 里 `stretch` 报告的盲区

`t_ns` 现在直接从**源帧时刻**换算,不从 `hold_ms` 累加。

⚠ 顺带发现:`stretch` 字段比的是 `gap_src` 和 `gap_play`,两个都从同一个
取整后的 `dt_ms` 算 —— **所以它看不见这 200ms 漂移**,30fps 素材上它报 1.0。
它能抓的是"帧间隔被 clamp"(`floored`/`ceiled`)那类失真,不是取整累积。

### 旧文件

`/1` 的包没有 `t_ns`,`from_dict()` 在**入口**用 `ensure_t_ns()` 从 `hold_ms` 累加补齐,
这样下游只需处理"每帧都有绝对时刻"一种情况。
⚠ 补出来的时刻**带着原有漂移** —— 旧文件本来就是那么录的,精度已经丢了补不回来。
要真正无漂移得从源(视频)重新生成包。`drift_ms()` 对这种包恒为 0,那本身就是标记。

## 串口性能 —— 别把 read(64) 写回来

`inspire_hand._txn()` 是所有读写的唯一出口。它按 `in_waiting` 增量收,**解析出完整帧
就立刻返回**。

曾经的写法是 `time.sleep(0.012)` + `read(64)`,这是"下发有延迟、报文卡住阻塞"的根因:

> pyserial 的 `read(n)` 会等到**攒够 n 字节或超时**才返回。回复帧只有 `nbytes+8` 字节
> (读 6 个 short = 20 字节),永远攒不到 64,于是每次事务都白等满 `timeout=0.5s`。

pty 假手实测(`build_read` 发帧、回合法 20 字节帧):

| | 旧 sleep+read(64) | 新 `_txn` | 倍数 |
|---|---|---|---|
| 单次读 ANGLE_ACT | 512.7 ms | 0.71 ms | 719× |
| 全量遥测(8 个事务) | ≈4101 ms | 5.3 ms | 771× |

也就是说每秒那一拍全量遥测会把 console 主循环**阻塞约 4 秒**,期间命令根本进不来。
真手比 pty 回环慢(20 字节线上 ≈1.7ms + 器件处理),预期 3-5ms,仍是百倍量级。

配套的两个循环改动(`hand_console.py`):

- **固定周期**: `next_tick += dt`,扣掉本轮串口耗时;旧写法是无条件 `sleep(dt)`,
  实际周期 = dt + 本轮耗时
- **阻塞 select**: 第一个 `select` 的 timeout 设到下一个 tick,命令一到立刻醒。
  旧写法 `timeout=0` + 末尾 sleep,命令最坏压满一个周期才被看到

实测(mock, 20Hz):周期中位 50.0ms / p95 50.0ms,命令生效延迟 0ms(旧:最坏 50ms)。

`txn_timeout` 默认 60ms(手回复 ~3ms,20 倍余量),它同时决定掉线时的降级速度。
首次握手 `connect()` 单独用 500ms —— CH340 刚上电用 60ms 会误判成掉线。

## 已知限制

1. **拇指弯曲行程压缩**: xls 实测 40° = 0.698 rad,URDF 限 0.6 rad,写角度只能到 86%,回读也在 0.6 处饱和
2. **手指耦合非线性**: P2/指腹/指尖关节 xls 偏离直线最多 11°,当前用 URDF mimic 的线性近似,精确的话得查表
3. **mock 和真手不能热切**: 接入时定死 mock 标志,要换得停掉重开
4. **URDF 和官方 xls 的 span 不一致,两处方向相反**(2026-08-06 查明):

   | | `HAND_LIMITS`(URDF) | `RAW_MAP`(xls) | 后果 |
   |---|---|---|---|
   | 四指 | 1.470 | 1.39626 | 命令 URDF 上限时 raw 饱和到 0(**行程没丢**),但**回报值虚高** —— `1.396/1.470 = 95.0%` 看着像"只能到 95%",其实已经到底 |
   | 拇指弯曲 | 0.600 | 0.69813 | URDF 更小,`rad_to_raw(0.6)=141`,**最后 14% 行程真的发不出去** |

   所以"四指只能到 95%"是**换算假象**,别当硬件限位;拇指那 14% 才是真丢。
   用角度做手型判据时要先消掉这个差,否则永远偏 5%。
5. **单次读寄存器失败率约 40%**,取终值要"连续两次读到相同"才采信。地址核对
   (`parse_reply(raw, want_addr)`)挡得住"答的是别的寄存器",挡不住**同一寄存器的旧值**。
6. **可行域只有一条约束、且只测了对角线**。已进 schema 校验(2026-08-08),但表是
   沿 `yaw = pitch` 扫出来的,`max(yaw, pitch)` 这个概括在非对角线上只有**一个**
   数据点支撑。中指/无名/小指没测(它们往外张、不与拇指相交,T1 里三根都到 raw 0),
   所以"通过校验"只等于"没撞上这一条已知约束",不等于"全查过了"。
7. **拇指弯曲少 14% 行程没定论**。URDF 限 0.6、xls 实际行程 0.698,`hand_pose` 的
   归一量按 `min(span, URDF上限)` 算,所以 n=1 落在 raw 141 而不是 0。厂家新 URDF
   给的 0.48 更紧,但那份 URDF 自己的拇指 limit 和 mimic 倍率互相矛盾,所以没照搬 ——
   到底哪个是真机械极限,还没在真手上量过。

## 安全

- **串口是只读的自检脚本默认不动手**,但调试页是运动控制,会发 ANGLE_SET 写帧
- **限位夹取**: 超出 URDF 限位的指令被裁剪到限位内,绝不外发原始越界值
- **退出前复位**: 收到 quit 指令先 set_angles(HOME_RAD) 让手张开,0.8s 后再断开,不留在握紧姿态
- **24V 供电必须合上**: 串口能开但读 HAND_ID 无响应会报错,检查电源和 RS485 A/B 接线
