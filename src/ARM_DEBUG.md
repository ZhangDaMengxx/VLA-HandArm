# 机械臂调试页

app_web.py 的第四个模式**「机械臂调试」**,用于单独调试 NERO 7 轴臂。
结构和「灵巧手调试」刻意一一对应,方便合体后同时驱动两者。

- 独立于「实时 Live」,不需要 ROS2 bridge
- 右侧滑块设定 7 个关节目标角,拖动只动 3D 预览,点『下发』才走 CAN
- 进页面即出 3D(离线也能当 URDF 浏览器用),接入 CAN 是另一个动作
- 遥测显示电流/力矩/速度/使能状态

## 和灵巧手页的三处实质差异

不是疏漏,是刻意的 —— 7 自由度工业臂的伤害量级和手不同。

| | 灵巧手 | 机械臂 |
|---|---|---|
| 默认模式 | **真机**(直接开 /dev/ttyUSB0) | **mock**(要接真机得显式取消勾选) |
| 运动前置条件 | 无,接入即可发角度 | **必须先『使能』**,急停后必须『复位』(复位内含重新使能) |
| 急停语义 | 定格当前位置 | **进阻尼模式,臂会缓慢下落**(无抱闸),按钮要确认 |
| 断开时 | 先回安全张开位再断 | **什么都不改**,只断 CAN |
| 切走 tab | 断开会话 | 断开会话(同「断开」,但不弹确认) |

## 断开 = 只断 CAN,原样交回

`arm_console.py` 的 `finally` **只 `disconnect()`**,不回零、不去使能。

臂的常态是被松灵客户端带电控制着,这个调试页是**临时客人**。客人走的时候把臂
原样交回去 —— 不改姿态、不改使能 —— 才是对的。

- **不回零**:臂在半途,回零路径未知,可能撞工装/桌面/自己。手可以安全张开,臂不行
- **不去使能**:实测失能仍靠伺服锁死(不掉扭矩),所以 `disable()` 既救不了"垂下来"、
  又白改一次臂的状态,还让松灵那边接手前要补一次使能。详见下面「使能 ≠ 掉扭矩」

切页和点「断开」走同一条路。区别只在**切页不弹确认** —— 切页是顺手动作,不该被
对话框卡住,更不该触发一次数秒的自主运动。

### 接入位姿 connect_pose

`connect()` 记下接入那一刻的 7 关节角。用途:

- **滑块起点**设成它,不是全 0。否则点『下发』第一下就把臂从当前位置拽到零位,
  那是个很大的、没人预期的运动
- **`{cmd:"goto_connect_pose"}`** 走回去,对应面板上「回到接入位姿」按钮
- 面板实时显示**与接入位姿的最大单关节偏差**(`pose_drift`,console 算好下发),
  超过 `ARM_DRIFT_WARN`(0.10 rad ≈ 5.7°)变黄
- 点「断开」时偏差超阈值就**弹一次确认**,告诉你偏了多少、问要不要先回位姿

### 为什么不做「切页/断开前自动急停 + 回原位」

考虑过,三个问题:

1. **顺序上做不到**。急停后关节进入阻尼模式,任何 `move_j` 都被拒,必须先 `reset()`
   才能动。"先急停再回原位"执行不了。而且急停**不保位**(见下),所谓"原位"急停后
   已经不是原位了
2. **切页触发运动很危险**。`move_j` 异步,发出去立刻返回、臂要走几秒。切页会变成
   "页面已跳走、臂还在自己动、没人盯着"。阻塞 UI 等它走完则是切个 tab 卡住数秒
3. **"原位"的路径未知**。`move_j` 走关节空间插值,路径不受控。回接入位姿比回零近,
   但性质一样 —— 沿途可能有障碍

所以改成:偏差**显示**出来 + 回位姿是**你点的、看着走的**动作 + 断开时**提醒**。
运动始终显式、可观察。急停按钮保持独立,那是给意外用的,不混进正常断开流程。

## 「复原」是哪个 —— 两个不同的东西名字撞了

```
0x150 Byte0 emergency_stop:  0x01 快速急停   0x02 恢复      ← reset() 发这个
```

> ⚠ **勘误(2026-08-03)**:这里原来还写了一条「0x150 Byte2 `grag_teach_ctrl`: 0x03
> 执行示教轨迹(拖动示教轨迹复现)」。**那是 piper 的协议,nero 没有。**
> 核实过:所有 `grag_teach_ctrl` 引用都在 `drivers/piper/` 和 `msgs/piper/` 下;
> `msgs/nero/default/transmit/` 里**根本没有** `arm_motion_ctrl.py` 这个文件。
> 错误来源是我拿"整个 SDK grep"的结果当成了 nero 的能力 —— 搜索范围 ≠ 事实范围。
> nero 实际有的示教相关接口见下面「拖动示教是连续的,但那条通道我们进不去」。

- **`reset()`** = `ArmMsgMotionCtrl(2)` = Byte0 填 `0x02`「恢复」= 退出关节阻尼模式。
  **不产生任何运动**,臂停在当前(可能已下落到的)位置。UI 上标「复位(解急停)」。
  ⚠ 光发它**还动不了** —— 协议流程第 8 条:「急停恢复后需要重新发送 `0x471` 指令
  使能电机方可继续运动」。所以 `NeroArm.reset()` 里紧跟一次 `enable()`,mock 和真机
  都做(否则 mock 走不到这条路径,真机上才第一次撞见)
- ~~**拖动示教里那个"复原"** 是 Byte2 的 `0x03`~~ —— 见上面勘误,nero 没这条。
  nero 的示教是主从模式(`set_leader_mode` / `set_follower_mode`),不是"录一条再复现"

SDK 里**没有**"回到某个位置"的复原。要回位姿只能自己记住再 `move_j`,即
`goto_connect_pose` 做的事。

## 急停**不是**定格 —— 臂会缓慢下落

协议流程第 8 条原文:

> 在运动过程中可发送 `id:0x150 byte0=1` 进行快速急停;急停状态全部关节电机进入阻尼模式
> (**由于没有关节抱闸,机械臂会缓慢下落**),发送 `id:0x150 byte0=2` 退出关节阻尼模式,
> 急停恢复后需要重新发送 `0x471` 指令使能电机方可继续运动

我早先说过"急停是阻尼制动,不掉扭矩、位置保持",**那是错的**,和上面这段直接矛盾。
阻尼模式只提供速度阻尼(抵抗快速运动),不提供位置保持力。重力会赢,只是赢得慢。

所以:

- 急停按钮**必须先 `confirm()`**,提示下方净空。它不是"安全地停住",是"以可控速度失控"
- 急停后 `_enabled` 置 `False`(mock 和真机都置) —— 电机进阻尼即失能。留着 `True`
  会让 UI 显示"已使能"而实际动不了
- `reset()` 里必须补 `enable()`,否则复位后仍然动不了

这和「使能 ≠ 掉扭矩」不冲突:**失能保持**(`0x471 byte0=1`)位置环还在响应,臂锁死;
**急停阻尼**(`0x150 byte0=1`)位置环停了,只剩阻尼。两个是不同的状态,别混。

## 接入必须轮询等,不能探一次

`robot.connect()` 只建 socket 并起后台读线程,**立刻返回,不等数据**。所有 `get_*`
读的都是 parser 缓存,缓存要等读线程解到帧才有值。踩过两次:

| 读什么 | 帧 | 频率(**实测**) | 不等的后果 |
|---|---|---|---|
| `get_joint_angles()` | `0x2A5/2A6/2A7/2A9` | **222.4Hz** | 回 `None` → 报"通了但读不到关节角" |
| `get_joint_enable_status(255)` | `0x261~0x267`(LowSpd) | **55.4Hz** | 回 `False` → UI 说"未使能"而臂是使能的 |
| `get_motor_states(j)` | `0x251~0x257`(HighSpd) | **220.5Hz** | position/velocity/current/torque |

> ⚠ **勘误(2026-08-03,固件 1.21 实测)**:这张表原来写 `~25Hz` 和 `~2Hz`,**都错了**
> 一到两个数量级(那是协议标称值,不是实测)。
> 命名容易反,记牢:SDK 里 **LowSpd = `0x261~0x267`**(带 `foc_status.driver_enable_status`),
> **HighSpd = `0x251~0x257`**(带 velocity)。名字和 ID 的大小顺序是**反**的。
>
> ⚠⚠ **同一天内我还改错过一次**:先报成 153.4 / 38.1 / 152.5Hz。错因是拿每个 ID 的
> 帧数除以**全局**跨度(所有 ID 合起来的 min..max),而不是该 ID **自己**的跨度。
> 自检信号很明显却被我忽略了:算出的"8 秒采样窗口跨度 11.59s"本身就不可能,
> 而且"吞吐率 153Hz"和"间隔中位 4.49ms(=222Hz)"两个数**不能同时成立**。
> 干净重测后三个数自洽:均值 4.493ms = 中位 4.498ms,`>20ms` 间隙 0 个。
> **教训**:速率一定要用该序列自己的首末戳算;吞吐率和间隔中位对不上时,先怀疑算法。

第二个更隐蔽:该接口 **"没数据"和"真未使能"返回同一个 `False`**,自身无法区分。
所以 `read_enabled(wait=)` 先等 `get_driver_states(1)` 出值(它 `None`/非 `None` 能区分),
再读使能位。真未使能时会等满 `wait`,所以只在接入时用,轮询循环里别传。

官方 demo 也是 `while + deadline`,但它在循环里发 `robot.enable()` —— 照抄会给未预期的
臂上使能,只读探测时要去掉。

## `0x151` byte6:不显式开就永远没有推送

推送开关的默认值是 `0x00` =「无效值」=**本次不改动**,不是「开」。所以单机接入时
臂可能压根不推 `0x2A1~0x2A9`,遥测全是 `None`。

`set_normal_mode()` 是 SDK 里唯一把 `enable_can_push` 置 ENABLE 的入口(置位后发一次
`0x151`,随即复位成 INVALID),已在 `NeroArm.connect()` 里调。副作用是同时下发单臂
主从配置 `linkage_config=0x00` —— 我们本来就是单臂直控,是想要的状态。

⚠ 接入时能读到值**不代表我们开过推送**,可能只是松灵客户端开过。那是它的状态,不是我们的。

## 官方时序:`0x471` 使能在 `0x151` 之前

```
2. 发送 0x471 使能全部关节电机
3. 发送 0x151 进入 CAN 控制模式
```

`set_speed_percent()` 发的正是 `0x151`。臂已使能时(接松灵客户端的常态)顺序无碍,但从
待机冷启动时抢先发 `0x151` 不符合官方时序。所以 `arm_console.py` 改成:已使能才立刻设
速度,未使能则挂进 `pending_speed`,等 `{"cmd":"enable"}` 成功后补发。

## 使能 ≠ 掉扭矩(别再推错)

`0x471` 的文档只写 `0x01 失能 / 0x02 使能`,**没说扭矩会消失**。我一度把"失能"
读成"掉扭矩",据此判断 `finally: disable()` 会让臂垂下来 —— **这是错的**,用户在
松灵客户端实测:失能后臂依然锁死,位置保持住。

驱动器的"使能"指的是**是否接受运动指令**(位置环是否响应),不是线圈是否通电。
这台臂没有失电抱闸(断电就垂),位置全靠伺服扭矩主动撑;失能后切进保持态,
仍在出维持当前位置的扭矩。

所以垂下来的条件是:

1. **断电**
2. **进入零力矩拖动/示教模式** —— `driver.set_leader_mode()`(zero force drag mode)、
   `0x150` Byte2 的拖动示教指令。这些才是设计上主动放掉扭矩的
3. 驱动器报故障自己失能

**不包括** `disable()`。

顺带一条也是错的:我曾说"失能长时间挂着有热风险"。抵抗重力的保持扭矩由姿态和
负载决定,和 `enable_flag` 无关 —— 失能保持和使能保持出的力、吃的电流、发的热
是同一回事。真要省电就折叠到重力力矩小的姿态,而不是切使能状态。

也搜过 CAN 沉默看门狗:**没有**。切到 CAN 控制后就算长时间不发指令,也不会自动失能。

## 架构

```
浏览器                  app_web.py                   后端子进程
  ↓                        ↓
点「机械臂调试」      (只加载 3D,不开 CAN)      three.js 在浏览器里跑
  ↓                        ↓
点「接入机械臂」      ArmDebugSession.start()   ┌─ arm_console.py(独占 can0)
  ↓                        ↓                    │    ↓ stdout JSON
点「下发」            POST /api/arm/command     │    └→ 广播给 /ws/arm
  ↓                    写 console stdin         │
WebSocket ← 遥测 ← _pump_console                └─ 退出时只断 CAN(什么都不改)

拖动滑块 → 不出浏览器(只改本地值 + three.js 预览)
```

### 断开的两个入口

| 动作 | 调用 | 弹确认 | 后端 |
|---|---|---|---|
| 切到别的 tab | `stopArmDebug({silent:true})` | 不弹 | 断 CAN |
| 点「断开」按钮 | `stopArmDebug()` | 偏差超阈值时弹 | 断 CAN |

两边都真的断开、都不改臂的状态。切回本页是离线的,要用重新点「接入机械臂」。

一个实现细节:关 WebSocket 前先把 `_armWs.onclose` 摘掉。不摘的话状态会被刷成
"连接断开",而这其实是我们主动断的,不是异常。

### 使能状态必须读真值

`connect()` 里调 `read_enabled()`(`get_joint_enable_status(255)` → 逐关节看
`foc_status.driver_enable_status`),**不能用本地默认 `False`**。

臂常态是被松灵客户端使能着的。用本地 `False` 会出现这个矛盾:臂物理上能动,
但我们自己的使能检查拒掉下发,页面报「臂未使能」,你被迫点一次多余的「使能」——
那一下其实只是在同步我们自己的标记。

`ready` 帧带 `enabled` 真值,`app_web` 把它塞进 `latest`,前端 `startArmDebug`
用 `j.enabled` 而不是写死 `false`。

## mesh:为什么不用原始的 nero_description

先跑一次 `python3 src/build_arm_viz.py`,产物在 `assets/viz/arm/`(已在仓库里)。

`assets/nero_description/urdf/nero_description.urdf` 浏览器**吃不下**,三个原因:

1. **visual 是 Collada(`.dae`)**,已 vendor 的 GLTFLoader 读不了
2. **`link2.dae` 有 24MB**(整套 dae 共 40.6MB)。同一几何的 `Link2.STL` 只有 1.7MB ——
   三角数一致(36049),差别全在 XML 的冗余上。浏览器解析 24MB XML 太慢
3. **路径是 `package://nero_description/...`**,浏览器不解析这种 URI

所以 `build_arm_viz.py` 拿 collision 的 **STL** 转 glb(几何等价,已核对包围盒),
输出 `nero_arm_viz.urdf` + 8 个 glb,共 **7.0MB**(dae 的 17%)。

> 没用 ColladaLoader 的理由:能 vendor(网络通),但它是 three.js examples 里维护
> 较弱的一档,而且解决不了 24MB 那个体积问题。
>
> 没用 trimesh 转 dae 的理由:需要 `pycollada`,环境里没装。STL→glb 只是把 float32
> 塞进 buffer + 一段 JSON,不值得为它加依赖,所以 `build_arm_viz.py` 自己拼 glb。

两个坑记一下:

- **glTF 规范要求 POSITION accessor 带 `min`/`max`**,缺了严格的加载器会拒收。
  手写 glb 最容易漏这条。
- **STL 的法线是逐面的**,直接用会让曲面看起来是刻面的。转换时丢掉法线,让
  three.js 自己算平滑法线(`computeVertexNormals`,在 `urdf_view._loadMesh` 里)。
- 原 URDF 的 `end_effector` 引用 **`stand_v1.dae` —— 仓库里没有这个文件**
  (dae 目录只有 `base_link` + `link1..link7`)。名字像底座支架被错挂到末端,是
  URDF 自身笔误。`build_arm_viz.py` 直接删掉那个 visual,免得浏览器每次吃个 404。

## Euler order:臂上比手更致命

`urdf_view.applyOrigin()` 用 `rotation.set(r, p, y, "ZYX")`。**别改成默认的 `'XYZ'`。**

URDF 的 `rpy` 是固定轴 RPY(`Rz·Ry·Rx`),three.js Euler 默认 order `'XYZ'` 算的是
`Rx·Ry·Rz`,只在**单轴非零**时才碰巧相等。手的 URDF 有 3 个关节两轴同时非零;
**臂的 7 个关节里有 5 个**(joint2..joint6)。

独立 FK 复算(不用浏览器):

| order | 零位末端位置 | 离基座 |
|---|---|---|
| `ZYX`(正确) | `[-0.0001, 0.0000, +0.7510]` | 751 mm,臂竖直站立 ✅ |
| `XYZ`(默认) | `[-0.0000, -0.0330, -0.4420]` | 443 mm,**末端扎进地里** ❌ |

`ZYX` 下各 link 高度逐节升高(0 → 0.138 → 0.448 → 0.718 → 0.751),xy 基本为 0。

### 零位是奇异位形,别误判成 bug

零位下 joint1/joint3/joint5 转 30° 末端位移是 **0.0 mm** —— 这三个轴在伸直姿态下
与连杆方向共线,是正常的奇异点。换个弯曲姿态(joint2=0.6, joint4=0.8, joint6=0.3)
就正常了:joint1→244mm、joint3→112mm、joint5→5mm。

joint7 只 17mm 也正常,它是末端腕滚,主要改姿态不改位置。

随机采样 3000 次最大伸展 750mm ≈ 零位 751mm,说明零位就是伸直态。

## 限位

`nero_arm.NERO_ARM_LIMITS`(来自 SDK 文档)是权威,前端滑块用它。
**joint4 和 joint6 不对称**,别按 ±same 生成滑块:

| | joint1 | joint2 | joint3 | joint4 | joint5 | joint6 | joint7 |
|---|---|---|---|---|---|---|---|
| 下限 | -155° | -100° | -158° | **-58°** | -158° | **-42°** | -90° |
| 上限 | 155° | 100° | 158° | **123°** | 158° | **55°** | 90° |

URDF 里的限位和这套差 <0.6°(URDF 存两位小数 rad 的取整)。查看器的 `setJoint`
按 URDF 夹取,所以滑块拉到 SDK 端点时显示最多差 0.6°,肉眼无感。

**2026-08-06 从真臂独立验证过**(`read_joint_limits.py` 读 `0x473`):七个关节的
角度限位和上表**完全一致**(误差 <2e-4 rad)。原来这套数只有 SDK 文档一个来源,
现在有臂自己的回报做交叉验证。

## 三层限制:关节级 vs CPV 轮廓级(2026-08-06 实测)

限制是**分层**的,搞混会得出错的结论:

```
电机物理能力              ← 手册没写,读不到(要转子惯量+减速比)
  └─ 关节级限制           ← 0x472/0x473/0x47C,read_joint_limits.py
       └─ CPV 轮廓参数    ← vv/ac/dc,read_cpv_params.py
```

### 速度

| | J1 | J2 | J3 | J4 | J5 | J6 | J7 |
|---|---|---|---|---|---|---|---|
| 手册额定 | 180 | 180 | 180 | **225** | 225 | 225 | 225 |
| 关节级(臂自报) | 179.9 | 179.9 | 179.9 | **179.9** ⚠ | 224.6 | 224.6 | 224.6 |
| CPV `vv` | 36.0 | 36.0 | 36.0 | 36.0 | 44.9 | 44.9 | 44.9 |
| `vv` / 关节级 | **20.0%** | 20.0% | 20.0% | **20.0%** | 20.0% | 20.0% | 20.0% |

⚠ **勘误。** 本文和 `nero_arm.py` 原来都写"`vv` 是**额定**速度的 20%,joint4 是例外
只占 16%"。**分母错了。** joint4 的关节级上限是 **179.9 而不是手册的 225**,
按臂里实际的设置算,joint4 也是 20.0% —— **七个关节没有例外**。

要问松灵的问题因此变了:**为什么 joint4 的关节级速度上限设成 180 而不是额定 225?**
(能不能提到 225 是另一件事 —— 那是写操作,而且见下面那个 scale bug。)

### 加速度:**没有余量**

| | J1 | J2 | J3–J7 |
|---|---|---|---|
| 关节级 max_acc | 114.6 | 114.6 | 143.2 |
| CPV `ac` | 114.6 | 114.6 | 143.2 |
| 余量 | **1.00×** | 1.00× | **1.00×** |

**逐关节完全相等。** 所以 143.2°/s² 就是天花板,`set_cpv_acc` 往上调没有意义。

这条把"要不要调参数"这个问题彻底关掉了:素材超上限**只能靠 retime 拉长时间轴**
(拉 k 倍 → 速度降 k 倍、加速度降 **k²** 倍)。

之前本文写"ac/dc 真实上限可能高好几倍" —— 那是**猜的,而且猜错了**。

### ⚠⚠ SDK bug:`set_joint_acc_limits()` 的 scale 差 10 倍

```
读: decode_47C   raw * 1e-3        → raw 2000 读成 2.0 rad/s²
写: set_joint_acc_limits           → round(v * 1e4)
    写 2.0 → 发出 20000 → 读回 20.0 rad/s²
```

两边都是 16 位字段(`ConvertToList_16bit` / `ConvertToNegative_16bit`),20000 装得进去,
**不报错**。而 `set_joint_acc_limits` 的 `check()` 拿 `round(abs(readback) * 1e4)`
和输入比 —— **用同一个错 scale 校验**,所以读回校验也会"通过"。

**结论:不要调用它。** 想写 2.5 会变成 25.0。好在余量 1.00× 意味着我们不需要写。

`ArmMsgFeedbackCurrentMotorAngleLimitMaxSpd` 上只有三个:

| docstring | 消息类实际 |
|---|---|
| `min_angle_limit` / `max_angle_limit` / `max_joint_spd` | ✓ 有 |
| `min_joint_spd` | **不存在** |

## 拒绝语义:HTTP 层也要诚实

`/api/arm/command` 对运动类指令(`angles`/`home`)**在 HTTP 层先查一遍**使能/急停,
不通过就回 **409 + 原因**。

理由:`ArmDebugSession.command()` 的 `ok` 只代表"写进了 console 的 stdin",真正的
拒绝是异步经 `/ws/arm` 回来的 `error` 帧,HTTP 响应反映不出来 —— 前端若信那个
`ok=true` 会显示"下发成功"而实际被拒。console 侧的检查保留(纵深防御),它才是
最终把关那道。

前端进一步在未使能/急停时直接**禁用**『下发』和『回零位』按钮,免得点了才知道被拒。

## 拖动示教是连续的,但那条通道我们进不去

反问得对:拖动示教复现**确实连续**,所以臂的控制器里**有**连续插值器。
那问题就不是"臂能不能连续走",而是"我们能不能把**外部算好的**轨迹喂进那条通道"。
这两件事我一开始混着说了,是错的。

核实结果:**喂不进去。** nero driver 里示教相关的接口只有这些 ——

| 接口 | 作用 | 方向 |
|---|---|---|
| `set_normal_mode()` | 单臂受控(`linkage_config=0x00`) | 发 |
| `set_leader_mode()` | 主臂**零力拖动**(`0xFA`) | 发 |
| `set_follower_mode()` | 从臂跟随(`0xFC`) | 发 |
| `get_leader_joint_angles()` | 读主臂角度 | **收** |
| `move_leader_to_home()` / `move_leader_follower_to_home()` | 归零 | 发 |

全是**模式切换 + 读主臂状态**。没有 `write_trajectory`、没有点位队列、没有缓冲运动、
没有 record/replay。示教轨迹是臂**自己录、存在臂内部**的,那个插值器只对它自己的数据工作。

### 唯一还剩的一条:主从遥操作

从臂跟主臂**必然是连续高频**的,而且是厂商设计好的通道。主臂角度走
**CAN 0x501–0x507**(`0x500 + 关节号`,一帧一个关节),decoder 是
`decode_leader_joint_state_by_index` → `from_bytes_to_float`(**裸 float**,
不是关节反馈那套 `0.001° int32`)。

但:
- 这个消息在 `msgs/nero/default/**feedback**/` 下,**不在 transmit/**
- 全 SDK 搜 `encode.*[Ll]eader` 只有 piper 的两条(`0x191` 归零、`0x470` 模式配置),
  **两条都不是注入关节角** —— 连 piper 也没有"喂主臂角度"的编码器

所以要走这条路只能**绕过 SDK 手搓 0x501–0x507 原始帧**冒充主臂。

**未验证(不要当成结论)**:从臂到底是不是从 CAN 总线上听 0x501+,还是走独立的臂间链路;
帧的字节序和 float 宽度;没有物理主臂时从臂会不会直接超时报错;跟随率和内部滤波是多少。
`_set_leader_follower_config` 有 `feedback/ctrl/linkage_offset`(0x00/0x10/0x20)三个偏移参数,
**暗示**多对主从可以共存一条总线 —— 那就暗示确实是总线广播,但这仍然只是推测。

⚠ 两个安全点:
- `set_leader_mode()` 是**零力拖动** —— 就是上面「掉扭矩的两种情况」之一,臂会垂下来。
  没人扶、下方没净空时**绝不能发**
- 它还 `enable_can_push = DISABLE`,进那个模式我们的**遥测就断了**

## 需求侧:轨迹到底要求多快(已算,不需要硬件)

`analyze_traj_demand.py`,离线跑 `out/robot_traj_*.npz`。帧率按源视频 30fps
(npz 里**没有时间列**,只有 `(N,7)` 角度矩阵,所以帧率必须外部给)。

跨全部 6 条轨迹,单关节角速度绝对值:

| | p50 | p95 | max |
|---|---|---|---|
| deg/s | **4.7** | **49.6** | 628.3 |

`>90 deg/s` 的样本占 0.28%–4.75%,`>180` 占 0%–1.45%。那个 628 是**视觉抖动尖峰**,
不是真实需求 —— 单帧 33ms 内跳 21°,人的手腕做不到。

结论:**需求侧一点都不激进**。稳态跟随只要 ~5 deg/s,p95 ~50 deg/s。
难点从来不是速度,是**平滑**和**别在尖峰处被当成阶跃猛甩**。这也说明供给侧实测该测的
不是"最高速多少",而是"给一个 50 deg/s 的连续参考,臂跟出来的形状变形多少、滞后多少"。

## 速度是**只写**的 —— 报出来的百分比曾经是编的

nero 上速度设了读不回来:SDK 只有 `set_speed_percent()`,没有对应的 get;
`0x2A1` 状态帧里也**没有**速度字段(唯一带 spd 的是「示教拖动超速」故障位)。
所以接入那一刻臂的实际速度是**未知**的 —— 松灵客户端上次设了多少就是多少。

真机上实测踩到的一串:

1. `arm_console.py --speed 20` 起的,但接入时 `read_enabled()` 拿到 False,
   于是速度被挂起(官方时序要求 `0x471` 使能在 `0x151` 之前,见上文)
2. 挂起值只在**我们自己**发 `{"cmd":"enable"}` 时才补。臂是被松灵客户端
   从外部使能的,那条路径不经过 `handle()` → **永远补不上**
3. 遥测却照报 `speed_percent: 100` —— 那个 100 是 `__init__` 里的**本地占位值**,
   从没跟臂核对过
4. 前端 `index.html:3573` 又把这个编的 100 同步进滑块,把 20 的安全默认冲掉

结果是「页面显示 100 / 臂里未知 / 我们要的 20」三者全不一致,而且**不报错**。

改法三条:
- `speed_percent` 属性在写成功之前返回 **`None`**,不返回猜的值。前端两处同步
  本来就有 `!= null` 判断,于是自动跳过,滑块保住安全默认
- `set_speed_percent()` **先发再记** —— 发失败就不改 `_speed`,免得显示幻觉
- 遥测循环里只要**观察到**已使能就补挂起的速度,不管是谁使能的

## 固件 1.11 → 1.21(2026-08-03 升级),实测变了什么

`detect_arm_firmware.py` 读到 **software_version = 1.21 → v120 driver**。
下面全是升级**之后**在实机上实测的(`candump` 和 python-can 都只听不发)。

### 总线速率:我原来写的数错了一到两个数量级

`candump` 实测总流量 **3424 帧/秒**(6s 窗口,20542 帧)。

| 帧 | SDK 名 | 实测 Hz | 间隔中位 | p95 | 载什么 |
|---|---|---|---|---|---|
| `0x2A1` | 状态 | 222.3 | 4.490ms | 6.01 | |
| `0x2A5/2A6/2A7/2A9` | 关节角 | **222.4** | 4.49ms | 6.15 | 7 个关节角 |
| `0x251~0x257` | **HighSpd** | **220.5** | 4.47ms | 6.30 | position/**velocity**/current/torque |
| `0x261~0x267` | **LowSpd** | **55.4** | 18.10ms | 19.79 | `foc_status.driver_enable_status` |

⚠ **名字和 ID 的大小顺序是反的**:LowSpd 是 `0x261+`,HighSpd 是 `0x251+`。
我第一遍就说反过一次。使能状态走 LowSpd(`get_driver_states`),velocity 走 HighSpd。

⚠ 这几个数我**改错过一次**(先报 153/38/152Hz),错因和自检信号见上面「勘误」那段。
SDK 自己的 `MessageAbstract.hz` 报 220Hz,和 candump 的 222.4Hz 一致 —— 两个独立来源
对上了。但 `hz` 在 connect 后 **0.1s 内恒为 0**(fps 管理器按 0.1s 窗口采样再乘 10),
接入就立刻读会拿到 0。

### 时间戳:CLOCK_REALTIME,分辨率 2⁻²⁰ 秒

SDK 的 `MessageAbstract.timestamp` 来自 `table_driven.py:57` 的
`cached.timestamp = rx_can_frame.timestamp`,而 python-can 的 socketcan 用
`SO_TIMESTAMPNS`(`socketcan.py:792`)。实测:

- 时钟基准 **CLOCK_REALTIME**(unix epoch)。与 `time.time()` 偏差中位 0.051ms
- 与 `time.monotonic()` 差 −1785431786 s —— **不同时钟,不可相减**
- 分辨率 **953.674 ns**,恰好 **2⁻²⁰ 秒**(= 1/1048576)。名字里的 NS 到不了 ——
  是 2 的幂说明从某个硬件/USB 计数器换算的,不是内核真纳秒
- 9406/9406 帧时间戳互不相同,内核确实逐帧盖戳

**但单帧戳不代表它在 CAN 线上出现的时刻。** 帧是**成批**到的:一批中位 **10 帧**
(p95 28、max 45),批间隔 1.87ms,30.5% 的相邻间隔 <0.2ms。走 usbip 过 WSL,
戳的是**批到主机**的时刻。要精确的帧间时序,这个戳不够用。

### 三个由此暴露的问题

1. **我们把硬件时间戳丢了。** `nero_arm.py` 从来没取 SDK 的 `.timestamp` / `.hz`,
   遥测里的 `t` 是**我们轮询那一刻**的 `time.monotonic()`
2. **严重欠采样。** 臂推 **222Hz**,`arm_console --hz 20` 轮 20Hz —— 每次轮询之间过了
   **11.1 帧**,只取最后缓存的 1 个,**丢弃 91%**
3. **臂手时钟不通。** 臂的硬件戳是 CLOCK_REALTIME;手侧**没有硬件戳**
   (RS485 不像 socketcan 有内核戳,时刻就是代码读完那一刻的 `time.monotonic()`)。
   而且 console 周期不同(手 33.3ms / 臂 50ms),采样点每 100ms 才重合一次

差分测速度的噪声地板(协议分辨率 0.001°):dt=4.49ms 时 0.223 deg/s,dt=50ms 时 0.020。
需求侧 p50 是 4.7 deg/s,两者都够 —— 但要用 222Hz 的原始戳,不是我们轮询的 50ms。

### CPV:总线余量够

1Mbit/s、8 字节标准帧含最坏位填充 132bit(132µs)→ 理论上限 ~7575 帧/秒。
现有 **3424 帧/秒 = 45.2%**(最坏)/ 38.0%(标称)。加 CPV:

| CPV 速率 | 增加 | 合计占用(最坏) |
|---|---|---|
| 20fps × 7 关节 | 140 帧/秒 | 47.0% |
| 30fps × 7 关节 | 210 帧/秒 | **48.0%** |
| 50fps × 7 关节 | 350 帧/秒 | 49.8% |

余量还够,但已经不是"三成"那么宽松了 —— 45% 底噪上再加 CPV,到 48%。

⚠ 真正的瓶颈**可能不是总线,是 usbip over WSL**。收方向已经看到成批到达,
说明 USB 是瓶颈层;发方向同理,210 帧/秒下发会不会被 USB 批处理拖出抖动 **必须实测**。

### 推送:1.12+ 上电自动推,`set_normal_mode()` 变成空操作

没有任何 console 在跑时 `candump` 3 秒收到 **10280 帧**。我一开始以为这**分不清**
"自动推"和"之前开过、状态保留到断电",要断电才能验 —— 其实 SDK 直接写着。
调 `set_normal_mode()` 时它 warn 出来的原文:

> Firmware ≥ 1.12 (`NeroFW.V112`): No effect (compatibility no-op). Only **leader**
> and **follower** modes remain (aligned with Piper). **Default is follower; CAN
> feedback push is on at power-up** — no manual CAN-push setup.

三个结论:

1. **1.12+ 上电自己就推**,不需要我们开
2. **`set_normal_mode()` 在 ≥1.12 上什么都不做**,只 warn 一句。所以
   `_enable_can_push()` 现在按 driver 分流:≥v112 直接跳过(记 `can_push_auto=True`),
   不去调那个空操作。跳过不等于失败,所以**不写 `last_error`** —— 写了会误报成错误
3. **默认模式就是 follower**。这跟「拖动示教」那节的主从注入线索直接相关:
   臂本来就在 follower 态,如果 leader 角度真的走 CAN 广播,那条通道是**现成开着**的

`connect()` 里先探再开推送的顺序**保留** —— 在 1.21 上是多余的 0.4s,
降级到 1.11 或换臂时是必需的。

## 现在的方案:离线把轨迹改成臂能走的形状

既然连续通道进不去、`move_j` 又会被逐帧抢断,方案就是**把难点搬到离线**:
在下发之前就把轨迹改成"稀疏路点 + 每段该花多久",让臂自己规划每一段。
`prep_arm_traj.py`,四步,每步都能单独关掉看对比。

| 步 | 做什么 | 改形状? | 实测代价 | 默认 |
|---|---|---|---|---|
| 1 夹限位 | 超 `NERO_ARM_LIMITS` 直接夹 | 是(边界处) | 每条轨迹夹 1–8 个元素 | **开** |
| 2 零相位低通 3Hz | 削视觉抖动 | 是 | p95 偏差 **~1°**,max 1.7–6.7° | **开** |
| 2b 再夹一次 | 低通过冲顶出限位 | 是(夹回) | 8–19 个元素 | **开** |
| 3 拉时间(retime) | 让速度落到上限内 | **否,恒 0** | 时长 ×k | `--retime` |
| 4 抽路点(RDP) | 780 帧 → 259 点 | 是(有界) | ≤ 容差 0.57° | `--rdp` |

⚠ **3 和 4 已改成 opt-in**(原来默认开)。理由:录制放慢之后不需要 retime,
时间轴保持均匀;均匀了就不需要 RDP,于是抽稀那 4.7mm 误差直接归零。
默认输出是 `mode="stream"` 的**全帧包**,给 `move_cpv_pos` 逐帧流式发。

⚠ **2b 是 2026-08-06 补的,原来漏了。** `clamp_limits` 在低通**之前**跑,而零相位
`filtfilt` 在被夹出来的折角处会过冲(Gibbs),把值顶回限位外面 —— 实测
`robot_traj_nero_inspire` 低通后 joint5 超限 **2.42°**、19 个元素越界,而上一步
已经报"夹干净了"。本文档 docstring 写着「超 `NERO_ARM_LIMITS` 的直接夹,
**不寄望下游**」—— 承诺和事实不符。是写 `combo_player.py` 的入口校验时被拒才发现的:
**六个包里五个中招**。第一次夹保留是为了报"原始素材本身越界多少",2b 是最终闸门。

### 三个写错过的地方,都记下来

**1. 限速不能"砍位移",要"拉时间"。**
第一版把逐帧增量夹到上界再累加回去。速度上界确实精确了,但那是在改形状 ——
实测**末端偏 76°**(joint6)。因为这些轨迹是真的需要 >90deg/s,不是个别尖峰;
砍掉的位移永远补不回来,越砍越落后。正确做法是形状一个字不改、该慢就慢:
每段所需时间 `dt_i = max_j|Δq_ij| / v_max`,和 `1/fps` 取大(只拉长不压缩)。
得到非均匀时间轴,形状偏差恒为 0,代价只有"总时长变长",而且变长多少是可报的。

**2. RDP 的度量必须和回放方式一致。**
第一版用**垂距**(点到线段最短距离),而回放是按**时刻**逐关节插值:
`q̂(t_k) = q_i + (t_k-t_i)/(t_j-t_i)·(q_j-q_i)`。该时刻对应的点不一定是最近点。
实测:垂距容差 0.573° 时真实重建误差 **5.78°**,超 10 倍。
量什么就保证什么,别用一个相关但不相等的量去代理。
范数也换了:用 **max-norm**(逐关节取最大)而不是 7 维欧氏 —— 限位、容差、
"偏了多少度"都是逐关节的概念,欧氏距离在这里没有物理意义。

**3. `N` 帧只界定 `N-1` 个间隔。**
`dur_src_s` 写成 `N/fps` 而 `t[-1]` 只累 `N-1` 段,算出 `stretch_x = 0.999`
—— "retime 把轨迹压短了"的假象。fencepost,不是精度问题。

### 起点不在零位 —— 这是安全要点

实测 6 条轨迹的起点距零位 **111°–158°**(最大的是 joint3 157.6°)。
所以**播放前必须先把臂从当前姿态挪到起点**,而那一步**不能**当成包里的第一个
路点顺手发掉 —— 那等于让臂从任意姿态猛甩到 -157°,中途路径由臂自己规划、
我们不可预测。包里因此单独导出 `approach` 段,让播放器把它当独立的、
要单独确认的一步:低速 + 有人看着 + 明确点确认。

另外 joint6/joint7 在两条轨迹上**超限** 0.6°/1.1°(边界擦碰,不是错),被夹掉。

### 播放器:`combo_player.py`(2026-08-06 写完,真机未跑)

臂 + 手**一条时间轴**,`ComboPlayer.tick()` 在调用方主循环里跑(不起线程,
和 `ActionPlayer` 同约定)。两侧都按各自包里的 `t_ns` **定位**,不累加。

CLI 三层护栏,和 `measure_cpv_jitter.py` 同级:默认 `--mock`(两边都不碰硬件);
真臂要 `--no-mock-arm` **加** `--yes`;`--dry-run` 只跑 preflight。

`preflight()` 查两条硬前提:臂**已使能**、`ctrl_mode == CAN_CTRL`。后者是
"跑完了但臂没动"的唯一防线 —— 松灵客户端把臂留在 ETHERNET 时,CPV 帧发出去
**不报错也不动**(SDK 的 `_cpv_po_joints_flag` 就是靠 `ctrl_mode != CAN_CTRL`
判断"链路断过"的)。

**跳帧策略两侧各判**,不能共用一个 flag:臂看包里的 `mode`;手看**帧间距中位数**
(<100ms 算流,可跳)。第一版拿臂包的 `stream` 管两边 —— 那会跳掉**人手编的关键帧**
(实测 `test1.json` 42 帧铺 20.3s、中位间距 200ms,那些驻留是有意的)。
流式素材跳帧无损(CPV 和 ANGLE_SET 都是**位置目标**,伺服本来要连续走过去),
关键帧跳帧就是丢动作。

`cpv_begin()` 里 `set_auto_set_motion_mode_enabled(False)` 是**必需的,不是优化**:
SDK 的 `_move_cpv` 每次都调 `_maybe_set_motion_mode('cpv')`,auto 开着时会**再发一次
0x151**。一个轨迹点 7 个关节 = 7 帧 CPV + 7 帧模式设置 = **14 帧**,30fps 就是
420 帧/秒 —— 正好是实测过的 210 帧/秒的两倍。不关 auto 跑的不是被测过的那条路径。
(这条是**读源码推的**:`_move_cpv` → `_maybe_set_motion_mode` → `set_motion_mode`
→ `_set_mode()` 发帧。想实测帧数但 SDK 在 vcan0 上不发帧 —— `connect()` 拿不到
关节角就不发,所以没有经验证据,只有源码证据。)

mock 下手侧**不能直接调 `write_shorts`** —— 它第一行是 `if self._sp is None: return False`,
而 mock 没有串口,于是每帧都"失败"(实测 42 帧全 fail 而回放看着是好的)。
`ActionPlayer._send_angles` 也是在调用方分流的,这里照做。

**升到 1.21 之后有两条路,不是一条:**

| | A. 稀疏路点 + `move_j` | B. 连续流 + `move_cpv_pos` |
|---|---|---|
| 驱动方式 | **到位驱动**(必须等到位) | **时钟驱动**(和手侧同构) |
| 为什么 | `move_j` 每条都是整臂规划请求,没到位就发下一条会**抢断** | CPV 是逐关节位置环 + 梯形轮廓,重设目标只是**重定向** |
| 要不要抽稀 | 要(259 点) | **不要**,780 帧直接喂 |
| CAN 负载 | 一点 1 帧 | 一点 **7 帧**(`0x181~0x187`),30fps = 210 帧/秒 |
| 形状保真 | 受 RDP 容差限(0.57°)+ 臂自己规划的路径未知 | 不抽稀就没有抽稀误差 |
| 已验证? | 原语在真机上用过(`move_j`) | **下发通路已验**(查询帧,210–1400 帧/秒);位置指令未发过 |

**B 是主路。** 下发抖动实测过了(见下一节):30fps 时线上组间隔 p99 34.26ms、
组内 7 帧散布只占周期 2.1%,一路到 200fps 都不丢帧。而且 B 让臂侧播放器**可以**
和手侧同构(都是时钟驱动),臂手时间轴漂移的问题跟着消失一大半 ——
不用再纠结"让臂当节拍器还是两边共用拉长后的轴",两边都按同一个时钟走就行。

A 保留作退路:`move_j` 是唯一在真机上真正驱动过臂的原语。

走 A 时 `dt_ms` 的语义是"**最少**等这么久",不是"到点就发"。到位判定用位置遥测
(实测 **222Hz**)在运行时测:连续 K 个采样内所有关节都在容差内才算到位,带超时兜底。
这样不需要预先实测每段要走多久 —— 那个数依赖速度百分比、负载、姿态,测不准。

### 发送抖动已实测:CPV 方案可行

2026-08-03 在真 can0 上测过(只发 CPV **查询**帧 `mode='r'`,不改臂状态;
测完核对关节角,最大偏差 0.395° = 重力下的正常抖动,**臂没动**)。

`--echo` 同时监听自己发的帧的**本地回环**。这比 `send()` 返回时刻有意义得多:
内核在 TX **提交**时 `can_put_echo_skb()`,在驱动报告 TX **完成**时才把回环帧投给
其它 socket。对 gs_usb 来说"完成"是设备通过 USB 回报的,所以回环时刻 ≈ 帧真正
发出去的时刻。`send()` 返回只说明"交给内核队列了",队列后面被 USB 批成什么样看不见。

| 下发率 | 帧/秒 | 线上组间隔 中位 | p99 | max | 组内 7 帧散布 中位 / p95 | 完整组 |
|---|---|---|---|---|---|---|
| **30fps** | 210 | 33.355ms | 34.26 | 34.29 | **0.479 / 0.698ms** (2.1% 周期) | 90/90 |
| 50fps | 350 | 20.019ms | 20.77 | 23.13 | 0.486 / 0.682ms (3.4%) | 150/150 |
| 100fps | 700 | 10.023ms | 10.66 | 11.43 | 0.475 / 0.601ms (6.0%) | 300/300 |
| 200fps | 1400 | 4.989ms | 5.69 | 7.42 | 0.481 / 0.617ms (12.3%) | 600/600 |

**结论:USB 批处理没有破坏下发节拍。** 一路到 200fps(1400 帧/秒)都是满组、
无丢帧、p99 在目标周期的 1.15 倍内。目标 30fps 时组内散布只占周期 **2.1%**,
一个轨迹点的 7 帧可以当同一时刻。

组内散布是**恒定的 ~0.48ms**,不随速率变 —— 那是 7 帧走一趟 USB 的固定成本,
不是速率效应。所以 200fps 那档"占周期 12.3%"只是周期变短了,绝对值没变差。

### 测这个的过程里踩了三个坑,都是测量代码自己的

1. **判据套错对象**。第一版给收方向也打了发方向的结论,于是只读模式下也印出
   「CPV 方案要重新评估」—— 看着像测了发送并且失败,实际一帧没发。
   收方向成批到达是**正常现象**,不适用"p99 超目标 2×"这个判据
2. **分组盲切**。按时间排序后每 7 帧一组,丢一帧就整体串位、跨周期取 min/max。
   症状很典型:50fps 档报组内散布 19.9ms(整整一个周期)、max 202ms,
   而 100/200fps 又正常 —— **"中间坏两头好"就是错位的指纹**,不是物理现象。
   改成用关节 1 的帧当组边界
3. **跨时钟对齐**。连着跑多档时,新进程的 listener 会收到上一轮残留的回环,
   于是"3 秒的测试里出现 3540ms 间隙"而完整组数又是满的 —— 两件事不能同时成立。
   我先用 `time.time() - (monotonic 已过)` 重建发送起点去过滤,结果 30fps 档
   90 组只剩 1 组(回环戳是 CLOCK_REALTIME、send 用 monotonic,跨时钟重建累积漂移)。
   改成发送前 `echoes.clear()` —— 不涉及任何时钟换算,精确
4. **判据只看 p99 漏判离群值**。那个 3540ms 的间隙 p99 才 11ms,被判成 OK。
   单次 3.5 秒停顿对回放是致命的(臂停在那儿)。改成 p99 和 max 都要过

`measure_cpv_jitter.py` 的三层护栏(实测过退出码):

| 命令 | 行为 |
|---|---|
| 不带 flag | **只测收方向,一帧不发**。exit 0 |
| `--send` | 默认只允许 `vcan*`;真通道直接拒。exit 2 |
| `--send --real` | 报清楚"要发 210 帧/秒查询帧",要 `--yes`。exit 2 |
| `--send --real --write-pos` | 会**让臂动**,单独警告 + 要 `--yes`。exit 2 |

即使查询帧(`mode='r'`,只读参数)也是往总线发东西,按项目约定要人明确授权。

收方向基线(只读):全 ID 合计 3429 帧/秒(独立复现了 candump 的 3424),
间隔 p95 0.806ms / p99 1.732ms / max 3.56ms。

⚠ 臂手时间轴漂移已经解决:两边都用**整数纳秒的绝对时刻**(`t_ns`),播放器按它
定位而不是累加。见 HAND_DEBUG.md 的「时间轴」那节。

### ⚠ 但臂**跟不上**素材:仿真出来跟踪误差 25–47°

下发通路验过了,不等于臂能走出那条轨迹。把速度+加速度受限的伺服按 1ms 步长仿一遍
(梯形轮廓,`vv`/`ac` 用出厂默认):

| 包 | 时长 | 跟踪误差 p50 | p95 | max | 最差关节 |
|---|---|---|---|---|---|
| `nero_gripper_rgb` | 11.8s | 8.0° | 39.5° | **47.4°** | joint6 |
| `raw` | 23.6s | 2.1° | 15.4° | 25.8° | joint5 |

**这个方向上是安全的** —— 伺服饱和意味着臂动得比指令**慢**,不是更快。但它意味着
第一次真机回放**验证不了通路能力**:测出来的是伺服上限,不是"CPV 能不能吃下 30fps"。

需求 vs 上限(`prep` 报告里的 `cpv_fit`):

| | p95 | max |
|---|---|---|
| 速度 / `vv` | **0.841×**(没超) | 14.4× |
| 加速度 / `ac` | **2.376×** | 23.7× |

**p95 的速度其实够,超的是加速度。** 所以"把 vv 提到 100%"解决不了问题 ——
平常动作没顶到速度上限。而加速度**没有余量**(见「三层限制」那节,1.00×)。

### 素材里有腕部翻转,retime 修不掉

仿真时发现一件不可能的事:`nero_gripper_rgb` 的 max 误差从 ×1 的 47.4° 涨到
×2 的 **58.0°** —— 慢放让跟踪**变差**。查出来是**阶跃**:

| 包 | 最大单帧跳变 | 位置 | 换算 |
|---|---|---|---|
| `nero_gripper_rgbd` | **21.6°/帧** | joint6,**第 0 帧** | 647°/s = **2.9× 额定** |
| `nero_inspire` | 17.7°/帧 | joint5,第 418 帧 | 531°/s |
| `nero_gripper_rgb` | 10.7°/帧 | joint6,第 221 帧 | 320°/s |
| `raw` | 4.4°/帧 | joint5,第 524 帧 | 132°/s |

不是孤立一帧 —— `gripper_rgbd` 头三帧连着 21.6/20.3/18.0,`nero_inspire`
第 417–419 连着 16.9/17.7/16.5。

**这是腕部翻转**(wrist flip):WiLoR 的姿态估计在某些角度下解跳到另一个分支,
IK 跟着换构型。3Hz 低通抹不掉它(不是噪声,是**真实阶跃**),慢放也修不掉
(位置空间里那个折角还在)。647°/s 是额定的 2.9 倍 —— **物理上做不到,任何参数都不行。**

`prep` 报告里的 `shape_dev_deg_max: 6.647` 一直在提示这件事,之前只看 p95(0.668)。

**必须在重定向层修**(解分支跟上一帧对齐的连续性约束),
在 `derive_embodiment.py` / `build_canonical_from_rgbd.py` 那边。
不修的话这个跳变会**直接进训练数据** —— 策略学到"这里要瞬间翻手腕",而真臂做不到。

`robot_traj_raw` 跳变最小(4.4°/帧)、限位余量最大(0.5°),是第一次真机测试的
最佳候选。它是最早那版,可能没经过引入翻转的那步处理。

### 修完之后要 retime 多少

按 p95 加速度 2.376× 算,retime **×1.54** 就落进上限(拉 k 倍降 k² 加速度)。
按 max 的 23.7× 算要 ×4.9(23.6s → 115s)—— **荒谬**,所以顺序是
「先修翻转,再 retime ×1.54~2」,不是反过来。

实测 retime 各档的跟踪误差(`raw` 包):

| | 时长 | 跟踪误差 p50 | p95 | max |
|---|---|---|---|---|
| ×1 | 23.6s | 2.11° | 15.44° | 25.76° |
| ×2 | 47.3s | 0.34° | 5.47° | 11.18° |
| ×3 | 70.9s | 0.13° | 2.09° | 4.98° |
| ×5 | 118.2s | 0.04° | 0.70° | 2.18° |

下降得比 k² 慢,因为跳变那几帧不服从这个规律 —— 又回到同一个根因。

## 要问松灵的(按优先级)

都是读了 SDK 和真臂之后**确定拿不到**的信息,不是没查就问。

1. **`joint4` 的关节级速度上限为什么是 180 而不是额定 225?**
   手册写 225,臂里读出来 179.9(`read_joint_limits.py`)。能不能提到 225?
   这直接决定 J4 的 CPV `vv` 能不能从 36 提到 44.9。

2. **`ac`/`dc` 的额定值。** 手册只有角速度。臂自报的关节级 max_acc(114.6/143.2°/s²)
   和 CPV 的 `ac` 完全相等,说明那已经是**当前设置的天花板**,但不知道**电机物理能力**
   是多少 —— 也就不知道那 143.2 是保守设置还是硬上限。
   按 143°/s² 从零加到额定 180°/s 要 1.26s,工业臂通常 0.1~0.3s,所以怀疑是保守的。

3. **`set_joint_acc_limits` 的 scale 是不是 SDK bug。** 读用 `*1e-3`、写用 `*1e4`,
   差 10 倍,而且 `check()` 用同一个错 scale 所以读回校验也会通过(见上)。
   如果确实是 bug,那 `set_joint_*` 这一族都要重新核对。

4. **离线轨迹能不能分段续灌。** `OFFLINE_TRAJECTORY_MODE(0x07)` + `0x151` 的
   `residence_time` 是"先灌点、臂按自己的钟执行"—— 那是唯一能摆脱传输抖动的机制
   (生效时刻由臂决定而不是由帧到达决定)。但 256 点上限装不下 557–780 点的轨迹。
   能续灌的话这条路就通了。

5. **`vv`/`ac` 改了断电保存吗,会不会影响松灵客户端。**
   如果是持久化的,那是改臂的全局状态而不只是我们这个会话。

6. **leader 关节角(`0x501–0x507`)能不能外部注入。** SDK 只有 decoder 没有 encoder。
   1.12+ 默认 follower,那条通道可能是现成开着的。见「拖动示教」那节。
