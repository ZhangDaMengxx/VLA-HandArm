# 合体页(实时 Live):臂 + 手同一个页面

app_web.py 的第二个模式。布局和「灵巧手调试」刻意一致 —— 左竖 tab 栏 + 中央 3D +
右侧只读监视。13 个滑块(臂 7 + 手 6),能分别下发,也能**联动**一起发。

## 走 console 路,不走 ROS bridge

```
浏览器                app_web.py                后端子进程
  ↓                      ↓
点「实时 Live」     (只加载 3D,不开通道)    three.js 在浏览器里跑
  ↓                      ↓
点「接入」          Arm/HandDebugSession   ┌─ arm_console.py (独占 can0)
  ↓                      ↓                │
点「下发」          POST /api/{arm,hand}/  │  └─ hand_console.py (独占 RS485)
                         command          │       ↓ stdout JSON
WebSocket ← 遥测 ← _pump_console ←────────┴──→ /ws/arm + /ws/hand
```

臂走 CAN、手走 RS485,**通道不冲突**,两个 console 可以同时在线。这一点
`ArmDebugSession` 的类注释早就写着了:「合体页面同时开两个会话即可」。

⚠ 老 Live 那条控制条(点动 / 使能 / 下发轨迹)走的是 **ROS bridge**
(`ros_joint_writer`),它会抢 console 已经独占的 can0 和 `/dev/ttyUSB0` —— 同一条通道
两个写者,后果不是报错而是**互相覆盖**。所以合体页把 liveBar 永久隐藏
(`test_combo_page_does_not_use_ros_bridge` 锁着)。ROS 端点保留没删(技能执行器还在用),
只是这个页面不碰。

## 「联动下发」

| 状态 | 行为 |
|---|---|
| 不勾(默认) | 下面「只发臂 / 只发手」二选一生效,按钮文字跟着变 |
| 勾上 | 目标选择行变灰,按钮变「下发(臂 + 手)」,**并发发两条** |

默认不勾:同时驱动两台设备的动作幅度比单发大,不该是默认。

**两条命令分别发,不合成一条。** 后端本来就是两个独立会话、两条通道,没有"同时到达"
这回事;硬合成一条只会在 app_web 里多一层假原子性 —— 一边成功一边被 409 拒的时候更难
说清到底动了什么。

实测偏斜(mock,两条命令同刻写进两个 console 的 stdin,60 次):

| | 中位 | p95 | max |
|---|---|---|---|
| 臂 ack 延迟 | 0.40ms | 0.75ms | 0.84ms |
| 手 ack 延迟 | 0.42ms | 2.37ms | 34.52ms |
| **两者偏斜** | **0.04ms** | 2.09ms | 34.04ms |

所以**单点联动的时间轴同步不是问题**。那个 34ms 离群是手的全量遥测那一拍堵住了循环。

### 只有一边可用的时候

臂要**已使能且未急停**才接运动指令,手没有这道门槛 —— 所以"一边能发一边不能"是常态。
三种状态分开显示:

| 情形 | 界面 |
|---|---|
| 两边都能发 | 正常提示 |
| 两边都不能 | 按钮**禁用** + 说明缺什么(未接入 / 未使能 / 急停中) |
| 只有一边能 | **只发能发的那边** + 黄字写明「本次只发 X,因为 Y」 |

第三种最要紧:静默发一半是最坏的 —— 界面显示「已下发」,实际只有手动了。而且
「未接入」和「未使能」要分开说,那是两个完全不同的动作要做。
`test_partial_send_is_reported_not_silent` 锁着这几条。

另外 dirty 标记**只在全部成功时**才清。清早了的话 3D 会切回跟实际角走,而实际角还没
到位,看起来像「下发了但没动」。

## mesh scale:那个「只看到法兰」的 bug

**症状**:合体页 3D 里只有一个零件,臂和手都看不见。

**根因不是 mesh 没加载** —— 19 个全部加载成功。是 `urdf_view.js` **漏读
`<mesh scale>`**:

装配 URDF 里法兰的 stl 是**毫米**单位(包围盒 39.5 × 38.65 × 25.0),靠
`scale="0.001 0.001 0.001"` 折回米。查看器不读这个属性,就按 **39.5 米**渲染。而
`_frameCamera()` 按整体包围盒取景 ——

| | 包围盒 | 取景半径 r | 相机距中心 | 臂(0.75m)占画面 |
|---|---|---|---|---|
| 修前 | 38.65 × 39.50 × 25.00 m | 30.330 m | 77.68 m | **1.2%** |
| 修后 | 0.14 × 0.27 × 1.06 m | 0.553 m | 1.42 m | **67.8%** |

臂在 77m 外缩成几个像素,所以画面上只剩那个放大一千倍的法兰。**看着像资源缺失,
其实是取景被一个件带跑了** —— 会让人去翻加载器和静态挂载,而那两处都是好的。

顺带验掉了这个修法的支点:three.js 的 `Box3.setFromObject` **确实认父节点的 scale**
(Node 里直接跑,1000.0× 精确)。

臂调试页没事,因为 `nero_arm_viz.urdf` 里没有任何 scale 属性 —— 法兰只存在于装配 URDF。

**为什么修在查看器而不是把 scale 烘进 glb**:scale 是 URDF 的合法语义,烘进产物只是
掩盖查看器的缺陷,下一个带 scale 的 URDF 会以同样的方式坏掉,而且坏的时候更难查。

三条测试锁着,都做过反向验证(把 bug 打回去确认测试真的失败):

- `test_urdf_view_reads_mesh_scale` —— 查看器读且 apply
- `test_scaled_mesh_still_needs_scale_in_product` —— 构建时不许丢掉 scale 属性
- `test_mesh_units_are_consistent_or_scaled` —— **数据**测试:折算后最大边长 <1m,
  换了新 mesh 也能挡住单位错

## 「改了不生效」:浏览器缓存

修完 scale 之后页面上仍然没变化,查了半天磁盘和服务端都是新的 —— 是浏览器拿了缓存里的
**旧 ES module**。ES module 按 URL 缓存,而这些文件名是固定的
(`/static/urdf_view.js`),改了内容 URL 不变,浏览器有权继续用旧的。

这类问题最难查,因为「文件明明改了」和「页面明明没变」两边都是真的。

修法是 app_web 加一层中间件,给所有静态路径打 `Cache-Control: no-cache, must-revalidate`。
**no-cache 不等于不缓存**:浏览器仍存着,只是每次带 ETag 问一句,没变就是 304
(实测 0 字节)。代价可忽略,而这个坑直接消失。

⚠ 别改成 `max-age` —— 那又会把 mesh 和 js 缓存住,踩同一个坑。

## 查看器的诊断输出

`urdf_view.js` 现在往 console 打三类东西,专门用来分辨「模型只显示一部分」的几种成因:

- **每次取景**:`bbox / r / 相机距 / mesh=ok/total`。r 远大于模型真实尺寸 = 有件被放大了
- **r > 3m 时警告** + 列出最大的三个 link,直接指出是哪个件
- **多个根 link 警告**:`find()` 只取第一个,其余整棵子树**静默不进场景** ——
  画面上少一大块而控制台一声不响(mesh 全加载成功了,只是没挂上)
- **孤立 link 警告**:joint 的 parent/child 引用不上,那棵子树整块看不见

加这些是因为光看画面分不清「mesh 没加载」「单位错把相机撑远」「子树没挂上」这三种,
而它们的修法完全不同。

## 修掉的一个已有 bug:切页不断会话

三个页面共用 app_web 里的 `_hand` / `_arm` **单例**会话。原来 `switchMode` 只在切回
「回放」时才清理 —— 于是**臂页 → 手页会把 CAN 会话留着**:手页显示「离线」,而臂其实
还被我们占着,松灵客户端也接不回去。

改成按「从哪来」显式拆一遍:

| 从哪个模式来 | 拆解 |
|---|---|
| 合体 | `leaveCombo()`(先断手再断臂 —— 手要 0.8s 复位到张开位,臂只是断 CAN) |
| 灵巧手调试 | `stopHandDebug()` |
| 机械臂调试 | `stopArmDebug({silent:true})` |
| 回放 | `stopLive()`(老 ROS 会话) |

`test_switch_mode_tears_down_every_previous_mode` 锁着四条来路。切页**不弹确认** ——
切 tab 是顺手动作,不该被对话框卡住,更不该触发一次数秒的自主运动。点页内「断开」才弹。

进页面时反过来:`enterCombo()` 查一次 `/api/{arm,hand}/status` 把在线标记和 WebSocket
接回去(否则会显示离线而后端会话还在跑)。`pollStatus()` 每 4s 反向纠正一次 ——
WebSocket 掉线只说明连接断了,不代表后端会话没了,两件事要分开判。

## ⚠ 2026-08-10:一个会污染联合回放的 stdin bug(已修)

`hand_console` / `arm_console` 原来用 `select.select([sys.stdin]) + sys.stdin.readline()`
读命令。那两个看的**不是同一层** —— select 看 fd,readline 看 `TextIOWrapper` 的
用户态缓冲。一次写进多行时,readline 把 fd 上的字节全抽进缓冲却只返回一行,
剩下的行卡在缓冲里而 fd 已空,下一轮 select 说"没数据",于是**要等下一条命令
到达才被处理**。

**为什么这会打到联合回放**:`_get_hand()` 是单例,技能路(`console_exec`)和
`_combo_start` 写的是**同一个** hand_console 的 stdin。一个手势技能展开成 3 行
(speed/force/angles),旧读法每次卡 2 行。所以:

> 先用语音发一个手势 → 再点 ▶ 联合回放 → 那 2 行残留会在**回放开始时**被读出来,
> 给手插进上一个手势的 force + angles。`start_at` 的 50ms 对齐余量当场作废,
> 两侧时间轴错开。

现象会像"联合回放偶尔手臂不同步",很难归因到手势技能上 —— 这正是本文档反复强调的
那类故障:共享时间轴只保证命令一起发出,任何一侧被延迟都会失同步。

**已修**:改用 `src/stdin_lines.py`(select 之后 `os.read` 直接读 fd、自己攒行)。
回归测试 `src/test_stdin_lines.py`,对旧读法失败 3/4。
**别把它"简化"回 readline** —— 这个 bug 从症状上看不出在读取层。

顺带验了合体包的大小边界:600 帧的包是**单行 73502 字节**,超过 `CHUNK=65536`,
跨 2 次 `os.read` 完整通过、600 帧没丢。现有实际包(`data/combos/*.json`)只有 2-3.5KB。

**部署前硬检查**(已知静默失败模式,必须拦):

1. **CAN_CTRL 前提**: 臂在 ETHERNET 模式下 CPV 帧**不报错也不动**,整段回放显示"完成"
   但臂纹丝不动。`verify_cpv_step0.py:351` 有 preflight 检查,但实际读回值未在真机验证
2. **加速度天花板 143.2°/s²**: 超过静默饱和。应在轨迹生成阶段逐帧计算需求加速度并拦截,

## 臂侧的轨迹播放器(原来整段是空的)

| 能力 | 手 | 臂 |
|---|---|---|
| 单点下发 | ✅ | ✅(本页) |
| 时序播放器(暂停/继续/驻留) | ✅ `ActionPlayer` | ✅ `combo_player.ComboPlayer`(CPV) |
| 技能包格式 | ✅ `gesture_pack.py` | ✅ `combo_pack.py`(臂+手同一个包) |
| 视频 → 关节 | ✅ 6 维 | ❌(`derive_embodiment.py` 出 13 维,但没页面能送真机) |

**播放器跑在 `arm_console` 进程里**,不在 web 层:CPV 要 `arm.move_cpv_pos()`,而 can0
被 console 独占。web 层先投递 `combo_prepare`，到位后再投递 `combo_start`，并轮询
`/api/combo/play/status` ——
进度**捎在臂遥测里**回来。语音说包名走的是同一条路(见 `README.md` 的「三种 kind」)。

⚠ 回放器 tick 必须排在**读位姿之前**。反了的话 CPV 帧在位姿读之后才发,遥测里带的是
上一拍的位置,进度看着比实际慢一拍。

### 端点

| 端点 | 动硬件 | 说明 |
|---|---|---|
| `GET /api/combo/list` `get` | ❌ | 列包 / 读单个包 |
| `POST /api/combo/save` `delete` | ❌ | 存包 / 删包,沙箱根 `data/combos/` |
| `GET /api/combo/check` | ❌ **只读** | 回放前体检,给确认框凑数据 |
| `POST /api/combo/play` | ⚠ **臂 + 手** | 见下 |
| `GET /api/combo/play/status` | ❌ | 进度,捎在臂遥测里 |
| `POST /api/combo/play/pause` `resume` `stop` | ⚠ 停/续 | `stop` 是停下发,**不是急停** |

`stop` 两侧**刻意不对称**:臂停在最后收到的目标位(**不回零** —— 回零路径未知,可能扫过
障碍),手用 `action_stop` 会 `set_angles(HOME_RAD)` **张开**。手张开是安全姿态(不夹
东西),臂回零反而危险。所以"停止"在两台设备上是两个意思,这是有意的。

`check` 单独开一个端点而不是塞进 `play`:确认框要**先给人看"会动多大"再让人点**。
`play` 里再查一遍(纵深防御)—— 两次之间臂可能被别的东西动过。

⚠ **`/api/combo/play` 会同时驱动臂和手,而 7860 没有任何认证** —— 同一网段的任何人都能
调。能力上和已有的 `/api/arm/command` 同级(那个也让臂动),差别是这里发的是**一串**而
不是一个点。**preflight 是唯一的防线**。

**preflight 分两层,查的东西不一样** —— 别以为 web 那层就是全部:

| 层 | 在哪 | 查什么 |
|---|---|---|
| web | `_combo_start()` | 臂/手未接入、臂未使能、急停中(`frozen`)、`mode == stream` |
| console | `ComboPlayer.preflight()` | 臂未使能、**`ctrl_mode != CAN_CTRL`**、手没连上 |

`ctrl_mode` 那条只在 console 层,而它是**「跑完了但臂没动」的唯一防线**:松灵客户端把臂
留在 ETHERNET 模式时,CPV 帧发出去**不报错也不动**(SDK 的 `_cpv_po_joints_flag` 就是靠
`ctrl_mode` 门控的)。web 层查不了 —— 它没有 `NeroArm` 句柄。

`arm_console` 还在 CPV 之前做两件事:**逐点查限位**(只查不夹)和 **`approach`** ——
以 50% 速度挪到首帧,挡住过大的初始落差。approach 是主循环中的非阻塞状态：
每个遥测 tick 继续读取并发布真实关节角，同时检查 0.5° 到位窗；所以 Web 3D 会显示
这段真实运动，而不是停住后跳到首帧。20s 超时、失能或急停都会拒绝正式回放。

帧间最大单关节跳变仍然要报,但走 CPV 之后**这个数的含义变了**:原来(`move_j`)大跳变
意味着规划被下一帧打断、臂走不到任何一个点;现在是位置环,重设目标不打断,后果是
**速度** —— 跳变越大冲得越快。`check` 只查不夹,夹了就把"包本身越界"这个事实抹掉了。

⚠ 退出 CPV 模式**只在 `done` 时做**,不在每帧结束时做。两个包之间退了的话,下一个
`combo_prepare` 又要重进,多一次模式切换。

`combo_player.py` 默认 `--mock`,真机要 `--no-mock-arm`/`--no-mock-hand` **外加 `--yes`**。

`move_j` **自带轨迹规划**,30fps 逐帧发等于每 33ms 打断上一条规划,臂永远走不到任何一个
点 —— 变成对目标轨迹做低通滤波(形状被抹平 + 整体滞后,滞后多少还取决于速度百分比)。
所以臂侧播放器**不能照抄** `ActionPlayer`。

能逐帧的原语取决于**固件版本**。**2026-08-03 已升级:主控 1.21 → SDK 走 v120 driver**
(`python3 src/detect_arm_firmware.py`,只读)。这解开了之前 v111 上的两个死结:

- **`move_cpv_pos` 可用了**。v120 继承 v112 的 CPV,是**逐关节位置伺服**
  (参数 `po` 位置 / `sp` 速度 / `ac`·`dc` 加减速 / `vv` 轮廓速度 /
  `pp` 位置环Kp / `kp`·`ki` 速度环)。和 `move_j` 是两回事:后者规划整臂轨迹、
  逐帧发会互相抢断;CPV 是每关节一个位置环 + 梯形轮廓,重设目标只是**重定向**,
  对伺服是正常操作。CAN ID `0x181~0x187`,一个轨迹点 7 帧
- **velocity 不再是 0**。v111 里那行 `motor_state.msg.velocity = 0.0`
  (注释:「corrected in version 1.20」)在 v120 的 `get_motor_states` 里没有了。
  ⚠ MRO 陷阱:**v112 没有自己的 `get_motor_states`,所以它继承 v111 的抹零** ——
  只有 v120 才是真速度
- 仍然可选的:`move_js`(无平滑无规划)和 `move_mit`(阻抗
  `T_ref = kp*(p_des-p) + kd*(v_des-v) + t_ff`)。`move_mit` 的代价没变:
  逐关节发、要调增益、是**力矩控制** —— 没有 `t_ff` 重力补偿臂会垂,
  稳态误差 ≈ 重力矩 / kp
- ⚠ **别用 `move_cpv_vel`**:SDK 源码里 7 个关节有 6 个被 `vel *= -1`,
  旁边标着 `# TODO: remove this after the bug is fixed`。位置版没有这个问题

**需求侧已经算出来了**(`analyze_traj_demand.py`,离线,6 条轨迹):
单关节角速度 p50 ≈ **4.7**、p95 ≈ **49.6** deg/s,`>180` 的样本只占 0%–1.45%
(那些是视觉抖动尖峰,不是真实需求 —— 单帧 33ms 跳 21°,人的手腕做不到)。
结论:难点**不是速度**,是平滑,以及别在尖峰处被当成阶跃猛甩。

`NeroArm` 现在只用了 `move_j`,几个流式原语都还没接。

### 拖动示教是连续的,但那条通道进不去

臂的控制器**确实有**连续插值器(示教复现就是证据)。但 nero driver 里
示教相关的接口只有模式切换(`set_leader_mode` 零力拖动 / `set_follower_mode`)
和读主臂角度(`get_leader_joint_angles`)—— **没有轨迹上传、没有点位队列**。
示教轨迹是臂自己录、存在臂内部的,那个插值器只对它自己的数据工作。
详细核实过程和唯一剩下的那条线索(主从遥操作 CAN 0x501–0x507)见 `ARM_DEBUG.md`。

另外 `video_gesture.py` 只出 6 维手,**完全不碰臂的 7 维**,而 `derive_embodiment.py`
早就在出完整 13 维 —— 离线管线的产物**没有任何页面能送到真机**。

## 时间轴同步(已实现:`combo_ready` + `start_at`)

**先做一次就绪握手，再共用一个 t0。** `combo_prepare` 只让臂低速到首帧，手不启动；
`arm_console` 到位后发 `combo_ready`。Web 收到事件才生成共同 `t0`，两个 console
**各自算自己的截止时刻**。正式回放没有主从、不需要周期性重同步。

已落到 `_combo_start()` 和 `_handle_arm_combo_event()`：收到 `combo_ready` 后取
`start_at = time.monotonic() + 0.2`，臂侧走 `combo_start`、手侧**复用 `gesture_play`**
并各带同一个 `start_at`。200ms 只覆盖两条 stdin 管道的调度和解析，不再错误地把耗时
数秒的 approach 塞进固定余量。approach 失败时手侧不会启动。

依据:`time.monotonic()` 在 Linux 上是 `clock_gettime(CLOCK_MONOTONIC)`,**系统级**的。
实测 200/200 次子进程读数都落在父进程的 `[a, b]` 区间内,偏移就是 IPC 往返本身
(中位 20µs)。所以两个进程的时间轴天然重合,不用交换时钟。

**`t0` 取未来的绝对时刻**(比如下发时刻 +100ms),不取"收到即为零点"。零点定在"各自收到
的那一刻"的话,上面测到的到达偏斜(p95 2.09ms、最坏 34ms)会**原样变成两条时间轴的固定
偏移**;定在共同的未来时刻,两边都先等到它,偏斜被整个吸收掉。这是唯一真正消掉偏斜的
一步,而不是量出来它很小然后接受它。

⚠ 这条是从测到的到达偏斜**推**的设计。代码已经这么写了,但**真机上没量过** ——
两条轴实际重不重合,要接上臂再测一遍才算坐实。

**手侧复用 `gesture_play`,没另造命令。** combo 包的手侧字段和 `GesturePack` 逐个对得上
(`hand_rad`→`rad`、`hand_raw`→`raw_vendor`,其余同名),转成 gesture pack 的 dict 就能
走 console 里已有的那条路,`to_action_sequence` + `ActionPlayer` 一整套时序/暂停/停止全部
复用。⚠ 一开始在 `hand_console` 里另写了个 `play` 命令自己拼 `ActionStep`,字段全错
(`angles` 要 0-1000 原始值不是弧度、`speeds`/`forces` 是 6 个的列表不是标量、驻留字段叫
`delay_ms`)—— console 直接 `NameError` 崩。

⚠ `return_home_first` 对 combo 包**强制 `False`**:第 0 帧就是录制那一刻的姿态,回零会在
正式动作前插一段**臂不知道的**手部运动,两侧时间轴当场错开。

**时间轴本身沿用手侧那套**:帧 N 的截止时刻 = `t0 + Σhold_ms[0..N-1]`,从**上一个截止
时刻**累加,不从 `now` 累加。从 `now` 累加会把 tick 量化误差逐步攒起来(实测 5.97s 素材
跑成 7.28s,慢 1.21×)。而正因为是绝对轴,**两条各自累加的轴天然重合** —— 两边算出来是
同一个数,这就是跨设备对齐的依据。

### 必须带落后检测

共享时间轴保证的是**命令一起发出去**,不保证**硬件一起到位**。只有臂会落后(手的
`set_angles` 近乎瞬时)。所以逐帧量 `lag(N) = 实际到位时刻(N) − 截止时刻(N)`,超阈值就
**报出来**,不要默默吸收。

理由:`hold_ms` 那个凭空拍的 80ms 下限,当时看起来"还行",实际整段慢 2.4×。静默吸收落后
是同一种失败模式 —— 而且更糟的是,**臂落后而手不落后的时候,两者会在共享轴上失同步**,
轴共享得再准也救不了。检不检测这个,是「构造上同步」和「真的同步」的区别。
